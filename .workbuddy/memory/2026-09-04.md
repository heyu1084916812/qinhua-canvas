## 同日第五次迭代：执行引擎语义重构（生成 = 节点内置动作 + 空槽位规则）

用户在确认拓扑/批量/结果组/陈旧标记四件套后，连续追问"点生成"的精确语义，发现**整个执行引擎的心智模型需要重构**——从"图片节点既是 sink 又是 source"改为"节点是 sink，「生成」是节点类型的内置动作，结果由各节点类型自己决定落哪里"。

**核心拍板**：

- 「生成」不是节点共有的属性，是**节点类型的内置动作**，由 `NodeDefinition.generate` 定义
- **两种执行模式**：
  - 单点生成（手动点某节点的「生成」）：只跑这一个节点，下游**不动**；结果按「空槽位规则」落 BFS 最近的空图片/视频生成节点；count>1 时累加找满 N 个；不够就在拓扑方向上自动铺新节点（命名 `原节点名的输出1`）
  - 拓扑生成（顶栏/右键 P 键/Ctrl+Enter）：按 Kahn 序串行，上游跑完才跑下游，**全部重跑**，下游吃上游最新输出
- **节点生成语义**（每类节点「点生成」行为）：

| 节点类型 | 怎么跑 | 下游槽数 | 结果落点 |
|---|---|---|---|
| 提示词 | LLM 改写文本 ×1 | — | 自己的文本框（覆盖） |
| 图片生成 | 调 API × count | count | count 个空槽位 |
| 视频生成 | 调 API × count（异步轮询） | count | 同图片，异步逐个落 |
| 批量节点 | **遍历内部素材 × count**（每素材一次 API） | **count × 内部素材数** | 空槽位 |
| 分组节点 | **1 次 API 调用**（所有素材一起进） | **创作面板「生成数量」参数** | 空槽位 |
| 对比 | 不可生成 | — | — |
| 画板 | 内部流水线 ×1 | — | 自己画板区域 |

- **批量 vs 分组**的精确差异：批量=N 次 API 调用每素材一份；分组=1 次 API 调用所有素材一起进，产出张数由创作面板参数决定
- **单点生成的边界**：触发节点本身参与 BFS；下游全满时弹菜单「覆盖最近下游/强制新建/取消」；按住 `Alt` 点生成则保留旧内容在触发节点拓扑方向铺新下游节点；拓扑生成期间不弹菜单直接强制新建
- **视觉标记极简化**（P1=A 的副作用）：陈旧标记**全部取消**，参数变化标记**全部取消**——只有拓扑生成执行期间（淡绿描边+进度）+ 失败（红框+错误图标）+ 选中（黑色边框）三种状态可见，节点在所有其他时刻完全静态

**P1 拍板 = A**（提示词改写后图片下游不动，用户自己手动跑），理由：单次生成不级联，陈旧标记语义被砍掉。

## 同日第六次迭代：拓扑生成降级为工具函数（用户核心洞察）

用户提了一个本质性的产品质疑：**AI 出图不是 100% 确定性**——拓扑跑一整条链路会把"不好的中间图"自动传给下游，整条跑完发现一半结果不满意，反生产力。

**用户原话**：「拓扑生成目前的使用场景只是一条可以直接复用的，不需要修改后面的流程的才会使用，批量和分组不属于这个方式，我怕这个拓扑生成没有使用场景，因为 ai 出图不是百分百出完全正确的，如果我建立了复杂的工作流后，用拓扑跑一整条工作流，其中一些不好的图可能会变成下游的素材，然后继续跑完结果，结果也不好」

**决策**：降级为工具函数，UI 完全不暴露。

| 层 | 处理 |
|---|---|
| UI 层 | 砍——画布顶栏无"全图重跑"按钮、无「仅刷新陈旧」按钮、无 P 键 / Ctrl+Enter / Alt+P 快捷键 |
| 工具层 | 保留——`traverseDownstream(nodeId, graph, callback)` 作为内部 API，供批量节点 / 分组节点 / 画板节点 / Agent 内部使用 |
| 心智模型 | 画布只暴露单点生成；批量场景 = 复制节点手动逐个跑（用户原意）|
