## 轻画架构文档：拓扑生成回归与架构审视

昨日（9-04）把拓扑生成降级为 `traverseDownstream` 工具函数。今日用户改主意——"拓扑那个保留，我还是要那个功能吧"。先把产品设计文档恢复拓扑生成为用户级能力，再审视架构后发现 12 项需讨论的问题，按 A/B/C/D 四类分组。

### 用户决策：「按你得来做」

倾向全做：A1-A4、B5-B7 全改；C8 画板子图快照改 + C10 agent 节点对齐改；D11 selection/viewport 语义修正 + D12 命令注释；**不做的**：C9 批量接口留后续。

### A 类（必改 4 项）

- **A1 TransactionBoundary 多步事务**：`multi-step` 模式 `{ mode: 'multi-step'; planId: string; label: string }`；planId 相同的连续 Command 共享一个撤销步骤，undo 一次性回退整次拓扑生成；每个 Command 仍独立 dispatch、独立 apply、独立持久化
- **A2 Command 联合拓扑入口**：加 `runPlan.execute(scope, mode, originNodeId)` + `runPlan.cancel(runPlanId)`，scope = 'node' | 'board' | 'global'，mode = 'rerun' | 'refreshStale' | 'rerunAll'
- **A3 节点指纹模块**：新增 `domain/canvas/graph/fingerprint.ts`，导出 `computeFingerprint(node, params, upstreamFingerprints) -> NodeFingerprint` 与 `findStaleNodes(...) -> NodeId[]`；指纹 = 显示快照哈希 + 参数哈希 + 入边拓扑哈希（递归）
- **A4 陈旧标记订阅**：新增 `features/canvas/staleness/`（`useStaleness.ts` + `staleStore.ts`）；订阅 graph → 重算指纹 → 与 liveFingerprints 比对 → dispatch `stale.mark`/`stale.clear`

### B 类（建议改 3 项）

- **B5 NodeViewProps 扩维度**：加 `stale: boolean` + `runMode: 'idle' | 'single' | 'topo-rerun' | 'topo-stale' | 'topo-all'`；`NodeViewEvent.requestRun` 加 `mode: 'single' | 'single-alt' | 'topo-rerun' | 'topo-stale' | 'topo-all'`，新增 `requestRunCancel`
- **B6 runEngine 取消级别**：从「单任务级 AbortController 透传」扩为「runPlan-level AbortController」——一次拓扑生成整次活动一个信号；取消时已成功的 RunTask 保留结果写回、未启动的跳过、正在跑的终止
- **B7 runEngine 回写路径**：runEngine 不依赖 dispatch（保持 shared 层纯净）；接收 `writeBack: (commands: Command[]) => void` 回调，由 CanvasPage 装配层传入 dispatch 包装器；multi-step 模式下第一个 Command 标注 `{ transaction: { mode: 'multi-step', planId } }`，后续同 planId 自动合并

### C 类（部分改 2 项）

- **C8 画板子图快照**：`buildRunPlan(scope, origin, graph, mode)`，`origin` 为 `{ originNodeId } | { subgraph: GraphSnapshot }`；`BoardCanvasHandle.getSubgraph(boardNodeId)` 提供画板内 children + 内部边
- **C10 agent 节点对齐**：`canvas/nodes/agent/` 目录预留但**节点注册表暂不收录 agent 类型**——产品形态未定；M0 只留 `features/agent/types.ts` 接口与目录；§5.9 加「节点类型状态」说明，与产品文档 §6.6 对齐
- **不做**：C9 `ChannelAdapter.batchGenerate` 留到性能成为瓶颈时再加

### D 类（架构健壮 2 项）

- **D11 selection/viewport 语义**：Command 联合里删 `selection.set` / `viewport.set`，改走独立 API `setSelection(ids)` / `setViewport(viewport)`；不进 dispatch、不进 undo 栈、不触发持久化；§4.3 唯一入口原则段扩充
- **D12 commands/ 命名歧义**：`state/workbenches/canvas/commands/`（UI → 命令总线派发层）≠ `features/canvas/execution/`（执行计划 + 运行时）；§3 目录树加注释区分

### 陈旧标记的特殊语义（关键洞察）

`stale.mark` / `stale.clear` **走 dispatch 但不进 undo 栈**——陈旧是「派生状态」而非用户意图，撤销应回到图本身的状态而非清掉陈旧标记。这条要在 §4.3 唯一入口原则段明示，避免后续实现误把陈旧加进 undo。

### runEngine 不依赖 dispatch 的边界价值

`runEngine(plan, deps)` 中 `writeBack: (commands: Command[]) => void` 是关键——业务测试可以直接喂 mock writeBack 验证执行逻辑，不必搭 store。这条让 `features/shared/execution/` 真正独立于工作台，与工作台并列架构正交。
