## 轻画架构文档：二次审视与 19 项全量修订

用户问「目前你觉得还有优化的地方吗？」——我做了一次深度扫读（通读架构文档 + 交叉比对产品文档），发现 **19 项**问题，分 A（产品-架构不齐必改 4 项）/ B（架构自身建议改 9 项）/ C（可选演进 6 项）三类。用户回复「全做」。

### 关键发现：产品文档内部有数据缺口

产品 §6.21 说「每个生成类节点保存所有 RunRecord，从不删除」，但 §12.1 的 8 张表里**没有 runRecords 表**，而 `tasks` 表有 500 条上限会滚动裁剪——版本历史若依赖 tasks 会被裁掉。
**决策**：新增 `runRecords` 作为第 9 张表（产品 §8 数据模型表 + §12.1 存储布局同步改），并写明两表分工：`tasks` = 运行日志（可裁剪，服务日志面板排障）；`runRecords` = 版本历史（永不裁剪，服务版本回溯）。

### 全量 19 项改动清单（架构文档）

**A 类：产品-架构不齐**
- **A1+C14** §4.5 `NodeDefinition` 补 `generate` 方法——产品 §6.19.2 早就写了「生成语义由 NodeDefinition.generate 定义」，但架构只有 `toRunRequest`。分工界定：`generate` 是主入口（返回 `GenerationPlan { calls, placement, slotCount }`，定义跑几次 + 落哪），`toRunRequest` 降级为单次请求构造辅助（简单类型实现它即可，复杂类型在 generate 内复用）。附各类型实现约定表（提示词 self / 图片视频 downstream-slots×count / 批量 ×素材数 / 分组 1 次 / 对比 null / 画板 board-internal）
- **A2+A3** §4.1 补 `RunRecord` 类型 + §4.3 Command 加 `node.runRecord.append` / `node.runRecord.restore` + §3 目录树加 `domain/canvas/model/runRecord.ts`。**LiveFingerprint 不单独建表也不存节点行内——它派生自 RunRecord**：节点当前生效 = 该节点 version 最大且 status='succeeded' 那条 RunRecord.fingerprint；「恢复旧版本」= 追加新 RunRecord（版本自增、沿用旧版数据）
- **A4** §4.1 补 `canConnect` 四条硬规则：① 输出只能连输入 ② **结果组不作为边端点**（组内标准节点才是端点） ③ **画板无端点、画板内外不建边** ④ 分组/批量子节点之间及与外部不建边
- **C15+C18** 指纹算法统一为 **SHA-1 截断 8 字节**（跟随产品 §6.19.6 基线；架构原写 sha256）。理由：陈旧判定不需要密码学强度，64 bit 在 300 节点量级碰撞概率可忽略，且指纹是每次 dispatch 后的热路径

**B 类：架构自身**
- **B5** `staleStore.ts` 从 `features/canvas/staleness/` 移到 `state/workbenches/canvas/staleSlice.ts`——**features 是控制器层不持有状态**，这是分层违规。§4.4 补 `StaleSlice` 接口（含 `replaceAll` 全量重算），useStaleness 改为只订阅 + 派发
- **B6** `writeBack` 加 `transaction?` 参数，**标记责任归 runEngine 而非调用方**（runEngine 知道 planId 与调用次序，整次 plan 首次调用传 multi-step 标记，后续不传）——避免「哪些 Command 属于同一次拓扑生成」这件事散落到调用方
- **B7** `buildRunPlan` 加 `staleNodeIds?: ReadonlySet<string>` 入参（refreshStale 模式必填）
- **B8** §5.5 明确 **useExecution 是宿主、runEngine 是纯执行器**：useExecution 持有 AbortController / writeBack 闭包 / taskStates / 生命周期；runEngine 不持有状态、不认识 React、不知道 dispatch，可喂 mock writeBack 单测
- **B9+B10** 新增 **§4.7 页面装配层**章节——CanvasPage 的四项接线职责（视图事件转命令 / 创建 writeBack 闭包 / runPlan 收尾落 RunRecord + stale.clear / 启动时 migrateDatabase → recoverInterrupted → recomputeStaleness）。**顺序不可颠倒**：先恢复再算陈旧，否则拿残缺快照比对会误标一批陈旧节点
- **B11** 引入 `RunMode` 类型 + **产品中文名 ↔ 代码标识符对照表**（idle/single/single-alt/rerun/refreshStale/rerunAll），Command 与 NodeViewEvent 统一引用它，消除两处各写字面量
- **B12** §2.2 依赖方向表 `workbenches` 行补 `platform`（画板导出需 files 端口、节点视图读能力元数据）
- **B13** Agent 运行时核心从 `features/canvas/agent/` **提到 `features/shared/agent/`**（会话循环/权限校验/React 绑定与工作台无关，漫剧工作台将来复用），画布只留 `features/canvas/agent/tools.ts` 工具实现

**C 类：可选演进**
- **C16** 补 `RunSummary` 类型（含 `records: RunRecord[]`，由调用方落库）
- **C17** multi-step 事务栈 **lazy 入栈**——首个携带 planId 的 Command 真正 dispatch 时才创建栈项，不在 buildRunPlan 时预先入栈（计划可能校验失败或用户提前取消，预入栈会产生空事务与幽灵撤销步骤）
- **C19** 路由懒加载在 §5.10（成本理由）与 §10 M0-9（执行步骤）整合，互加交叉引用

## 实施节奏：M0 拆 4 个对话 + 建交接本

用户问「是否要开始隔离对话，M0-1 一个对话 M0-2 一个对话」。

**结论：要隔离，但 10 步拆 10 个对话太碎**（每开一个都要重读架构文档，交接成本 > 收益）。按「这段代码需要什么知识」分 4 组：

| 对话 | 内容 | 分组理由 |
|---|---|---|
| 1 纯逻辑地基 | M0-1 目录骨架 + M0-2 领域纯函数 + M0-3 平台端口 + **M0-10 检查门禁** | 全程不碰 React/UI，上下文干净，单测即验收 |
| 2 状态内核 | M0-4 命令总线 + 事务撤销栈 + 持久化 + createStore 工厂 | M0 最重一步，要反复啃 §4.3 契约，混一起会被稀释 |
| 3 纵向切片 | M0-5 画布骨架 + NodeFrame + 注册表 + 提示词节点全链路 + **M0-6 tokens/motion** | 可见部分；tokens 必须与组件同批写，否则先写字面量颜色再抽 = 写两遍 |
| 4 扩展位收尾 | M0-7 陈列室 + M0-8 Agent 占位 + M0-9 工作台插槽 + 全链路回归 | 三项都是插座位性质，各半小时 |

**两处刻意调整**（重要，别在后续实施中改回去）：
- **M0-10 门禁提前到对话 1**——等对话 2/3 写完再补 dependency-cruiser 会一次性爆几十条违规，那时改架构比现在贵得多
- **M0-6 tokens 提前到对话 3**——与组件同批出生

### 关键解锁：渠道与 Key 不阻塞 M0
M0-3 验收标准是「状态层可在无浏览器环境跑通」，用内存实现 + mock 适配器即可满足。真实渠道是 M1 接生图才需要——**这个决策推迟到 M0 跑通后**，不再是开工阻塞。
