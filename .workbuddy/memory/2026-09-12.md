### 拍板了三个此前悬而未决的问题

M6-8 与 M6-9 两度推迟这条方向，原因就是「先得定：页码打在哪、是否随跨页版式变、是否可关」。本次定：

| 问题 | 定论 | 理由 |
| --- | --- | --- |
| 打在哪 | **页脚带**（页下延伸 4.5% 页高的留白带），不是画面内角标 | 压在格子上会挡内容，投稿/印刷不可接受；带与页同底色，视觉就是书的页边 |
| 随跨页变吗 | **不变**——跨页时两页**各一条带**（被中缝断开，像摊开的书） | 页码跟「页」走，不跟「图」走；每页一条带使单页/跨页只有一套规则 |
| 可关吗 | **可关且默认关** | 导出 PNG 常直接投稿/印刷，页码是阅读辅助不是画面内容；误开要重导才能去，代价不可逆 |

**页码帖「外侧」（切口侧）**：跨页时槽 0 靠左、槽 1 靠右；单页没有中缝可参照，退化为阅读终点侧（`ltr` 右下 / `rtl` 左下）。关键点：**锚点由视觉槽位决定、与页序无关**——`rtl` 下槽 0 放的是较晚的页，但它的页码仍在左。

## M6-12 渠道层消费 `inputs`（跨层补洞，已完成并收口）

**落地结构（5 处）**：
1. `domain/shared/execution/inputs.ts`（新，纯函数）：`flattenInputs`（递归摊平 collection）+ `imageInputsOf`（只留 `image/*` → 按 `assetHash` 去重 → 截断 `MAX_IMAGE_INPUTS=4`）。`collectionItemId` 刻意不参与去重（它区分的是「同一 plan 第几次调用」）。

3. `ChannelDeps` 改为 `Pick<PlatformKit,'network'|'assets'>`——装配处直接传 `platform`，5 处调用点零字段搬运。

## M6-13 角色卡参考图上传（comic 侧最后一个缺口，已完成并收口）

**问题本质**：`ComicCharacter.referenceHashes` 自 M6-2 就在模型里，命令层 `character.update`（`ComicCharacterPatch`）一直支持 patch 它，M6-12 更让渠道真的会读它——但**界面上没有任何地方能把一张图放进角色卡**。字段齐全却填不进去 = 这条链路只差用户能碰的那一下。属「有模型、没入口」。

**落地结构（4 处）**：
1. `domain/comic/model/comicProject.ts`：加参考图列表语义 `addCharacterReference(hashes, hash)` / `removeCharacterReference(hashes, hash)`。**命中「已在列表里 / 本来就不在」时返回原数组引用**——关键，见下。
2. `domain/shared/hash.ts`：加 `fingerprintBytes(bytes) = sha1Bytes(bytes).slice(0,16)`——与 `fingerprintHex` 同口径（同截 16 hex），使「上传的图」与「生成的图」在 `assets` 表里形状一致。注释里写明它与 `fingerprintHex(model|prompt|idx)`（**请求**指纹）是两件事（**内容**指纹）。
3. `workbenches/comic/surface/characterRefUpload.ts`（新）：依赖注入 `{ pickFile, putAsset }` 两件口的上传器 → `pickAndStore()`：选图 → `blob.arrayBuffer()` → `fingerprintBytes` → 写 `assets` 行 `{id:hash, hash, mime, bytes}` → 返 `{hash, mime}`。**无需浏览器即可单测**。
4. `workbenches/comic/surface/ComicSurface.tsx`：`useMemo` 建 uploader（`pickFile: platform.files.pickFile` / `putAsset: platform.storage.put('assets', row)`）；角色 `<li>` 改**纵向两行**（`.charRow` 名字/描述/删除 + `.charRefs` 参考图行）；新增 `CharacterRefThumb`（`useAsset(hash)` + 移除按钮，`data-comic-character-ref` / `-ref-remove` / `-ref-add`）；CSS 加 `.charRow/.charRefs/.charRefsLabel/.charRef/.charRefImg/.charRefRemove/.charRefAdd`。

### 关键设计判断

1. **素材落库不走命令、直写 `assets` 表**。最初设想是 dispatch `asset.put`——但那是 **canvas 的命令**，comic 的 `ComicCommand` 联合里根本没有它，而且 comic 的 reducer 只返回下一个 `ComicProject`（单聚合对象、无补丁流），**结构上没有「素材写」的通道**。恰与 `ComicExecutionProvider` 写生成产物**同一条路径**（`platform.storage.put('assets', {...a, id: a.hash})`）——素材本就与项目文档分离落库（`assets` 表 vs `comics` 表）。所以不需要、也没给 comic 引入 `asset.put`。
2. **去重语义收在模型层且返原引用**。`updateCharacter` 靠 `next.referenceHashes !== prev.referenceHashes`（**引用比较**）判「是否真变化」。若在此无条件 `[...prev, hash]`，重复添加同一张图会被当成真改动、白写一次项目文档。切分正合：模型层定义「有没有变」，surface 只负责「变了就派发」。
3. **内容寻址的幂等红利**：上传的图与生成产物共用 `assets` 表、共用「id 即内容哈希」约定 → 同图重传是幂等 upsert（不产生第二行），换文件名再传也不会被当成新图。**「同一张图」由字节决定，不由文件名决定**。
4. **命令层不认识 `Blob`，素材层不认识角色卡**，中间靠 hash 这个稳定标识解耦；上传器可脱离浏览器单测（注入假 `pickFile`/`putAsset`）。
5. **异步上传后取最新角色再派发**：`onClick` 里 `await pickAndStore()` 之后**从 `store.getProject()` 重取角色**（而非用渲染闭包里的 `c`），否则连续上传两张时后一次会用旧列表覆盖前一次。

## M6-14 对白贴纸尺寸手柄与拖尾巴改指向（M6-4 的两条欠账，已完成并收口）

### 补的是什么洞

M6-4 之后对白贴纸**只有「位置」可改**：`x/y/w/h/tail` 早在 `ComicBalloon` 里，但界面只能拖 `x/y`——**尺寸从 `defaultBalloonRect` 建出来那一刻就定死**（60%×16%），文字一长就溢出且无解；`tail` 只能跟着平移（`movedBalloonRect`），**指不了说话人**。两条是 M6-4 同一条推迟记录、同一交互模型，捆成一组。**未加数据字段、无迁移**——只是终于能从界面上改这三个量。

### 关键设计判断

1. **一条不变量收住两个坏手感**：气泡与尾巴**作为一体**参与平移（保*相对偏移*）与缩放（保*相对比例*）⇒ **唯一**能改变尾巴相对位置的操作是显式拖尾巴。少了这条会**同时**冒出「拖走气泡、尾巴留在原地」和「放大气泡、尾巴被吞进气泡里」两个 bug——各自看起来都像独立缺陷，实则同一个不变量缺失。写代码前先想清「哪几个操作是一体的、哪一个是显式的」，比事后逐个打补丁省事。
2. **三条直接操作 = 三条命令，刻意不合并**：`balloon.move` / `balloon.resize` / `balloon.moveTail`。「位置 / 尺寸 / 尾巴」是**正交自由度**，各自由不同手柄触发、几何规则不同（平移喂目标位置、缩放喂目标尺寸）；合并进一个 `patch` 只会在 reducer 里长出 `if (patch.w !== undefined && patch.x === undefined)` 式分支。
3. **预览与提交必须同源，不是「两套近似实现」**：`BalloonLayer` 的拖拽状态机改成存**起点快照 `base` + 抓取偏移**，指针移动时调 domain 的那三个纯函数，松手把**同一份结果**抛给回调。于是「手指底下看到的 = 落库的」是**结构性保证**而非巧合；存快照（而非逐帧累加）也顺带消掉了浮点漂移。
4. **`movedTail` 无尾巴返 `null`**：「不可拖」与「拖了没动」在**类型上**就分得开，reducer 拿到 `null` 直接视为无变化、返原引用——不必再判 `hasTail`。
5. **尾巴的堆叠必须分两态**：只读时尾巴画在气泡**下面**（只露尖角，维持原视觉）；可交互时改画在**上面**并把命中区放大到 13px（槽位定长 + 居中 7px 菱形，几何与原来一致）。否则尾巴一旦被拖进气泡里就**再也抓不回来**——同理可交互态尾巴底色换深一档，白底白框在气泡上等于隐身。

## M6-15 comic 生成留痕与版本回退（#161–#165 收口）

**动机（定性：不可逆数据丢失，不是缺功能）**：M6-5 落地 `ComicPlacement.record()` 时**明写「暂不落留痕」并返 `null`**，于是 comic 格「点一下重生成就丢一版图」——旧 `assetHash` 被覆盖后画面再无指针指向它（素材字节仍在 `assets` 表，成了**孤儿**）。本轮把「留痕」这条腿接上。

### 三条不变量（贯穿代码 + 文档）

1. **只增不减**：留痕是「发生过的事」，任何操作都不删（产品文档 §6.21）。comic `canUndo()` 恒 false，历史永不回退删除。
2. **版本号由历史自身推出**（`nextPanelRunVersion` = max+1），**不由调用方给**——载荷类型 `PanelRunInput = Omit<ComicPanelRun,'version'>` 把这条**变成类型约束**，堵死「两条 v3 / 跳号」这类界面看不出来的错误。调用方想传 version 都传不进来。
3. **回退本身追加为新版本**：`restorePanelRun` 写回输入与产物后 **append 一条新留痕**（而非把指针拨回旧版）——历史永远只增，不需要 undo 栈兜底。

### 关键设计决策

1. **留痕存储位置由数据形态决定**：canvas 是「图 + 补丁流」双存储 → 留痕另落 `runRecords` 表；comic 是**单聚合对象、单写通道**（整对象防抖落 `comics` 一行）→ 留痕作为 **`ComicPanel.runs`** 住在格内，随项目一起读回/导出/归一化，**不给 comic 另开表**。开表会立刻制造「两处真相要同步」的问题。
2. **快照口径只记影响画面的字段**：`scene`/`shot`/`characterIds`/`channelId`/`model`/`referenceHashes`/`fingerprint`/`outputHashes`。**不含对白贴纸**（不烘进图、回退不该动它）与转场 `transition`（是叙事关系不是画面，回退时保留面板当前转场）。
3. **`assetHash`（画面真相）vs `livePanelRun`（历史真相）分工**：正常两者一致，**唯一分叉 = 成功但渠道没回图**。UI 的「当前」标记挂在 `livePanelRun`，缩略图锚在各自 `outputHashes[0]`。
4. **回退守门 `canRestorePanelRun`**：只放行 `succeeded && outputHashes.length>0`；失败版本**如实留痕**但界面灰掉（「发生过」与「能回去」是两件事，不能因为不能回去就不记）。
5. **`panelRunFromRecord` 沿用引擎 `record.id`** 作留痕 id（幂等 + 两表对查）；参考图走 `imageInputsOf` 同口径（去重 + 上限 4），保证历史里记的参考图数 = 当时真正喂进去的数。

### 冒烟竞态修复（G38 假失败，与本组功能无关）

首次全量冒烟 534/535，唯一失败是 **G38「上传后出现 1 张参考图缩略」**（M6-13 的功能）。判定依据：**紧邻的下一行断言「缩略图可解码为真实 PNG（8×8）」是通过的**——缩略明明出现了。根因是断言写法：

```js
await fc.setFiles({ ... })                                   // 触发异步链
rec(g, '上传后出现 1 张参考图缩略',
    (await page.locator('[data-comic-character-ref]').count()) === 1)  // ← 立即求值，无等待
```

`setFiles` 之后是 **读文件 → 写 `assets` 表（异步 IDB）→ dispatch → 重渲染** 一整条链路；下一行之所以稳，是因为 `sampleImgPixels(..., {tries:24})` **自带重试**。

**通则（可复用）**：**「触发异步动作 → 立刻数元素」是必然竞态**，尤其链路里含 IDB 写入/素材解码时。判据很好认——**同一位置的下一条断言如果带重试/等待却通过了，就说明是断言的竞态而不是产品 bug**。凡是断言元素**数量**，用 `waitSelectorCount`；断言元素**状态**（可见/文本）用 `locator.waitFor`/`waitForFunction`。**不要用「它上次是过的」来把偶发失败归为 flaky**——先看它的下一步断言是否自洽，能定性就别重跑覆盖。

### 一、连线不可见：根因已定位（重大缺陷）

**现象**：画布上**所有连线都看不见**，包括拖线过程中的草稿曲线。DOM 里查得到、能命中、样式正常，就是不上屏。

- `[data-edge]` 路径存在，`d="M 240 80 C 280 80, 280 120, 320 120"`、`stroke=rgb(201,201,209)`、`stroke-width=1.5px`、`opacity=1`、`visibility=visible`；
- `getBoundingClientRect()` = `{x:248,y:88,w:80,h:40}`——**几何真实且在屏内**；
- `elementFromPoint()` 沿曲线取三点，全部命中 `path._hit`——**命中测试也正常**；

**隔离实验**（`scripts/probe-svg-zero.mjs`，4 组对照）：
| 实验 | SVG 尺寸 | overflow | 是否绘制 |
|---|---|---|---|
| A | **0×0** | visible | **否** |
| B | 200×200 | 默认 | 是 |
| C | 1×1 | visible | 是 |
| D | 1×1 | 默认 | 是 |

**结论（通则）**：**Chrome 对退化尺寸（0×0）的 `<svg>` 完全不绘制其内容，`overflow: visible` 也救不回来**；只要尺寸非零，`overflow:visible` 就能把内容画到框外。**「DOM 有 / 能命中 / 样式对」三件事都成立，却依然可以画不出来**——`count()` 与 `elementFromPoint()` 都证明不了「已绘制」。

**本项目命中**：`src/workbenches/canvas/layers/EdgeLayer.module.css` 的 `.svg` 是 `width:0; height:0; overflow:visible`，父级 `.world` 同为 0 尺寸（0 尺寸 div 靠 overflow 溢出是**有效**的，节点正是这么显示的——所以这个 0 尺寸写法被误当成了「安全惯例」照抄到 svg 上）。

**为什么冒烟全绿也没抓到**：全量冒烟里所有连线断言都用 `page.locator('[data-edge]').count()`——**只查 DOM 数量，不查是否绘制**。这是一个系统性的断言盲区（同类风险：`[data-edge-delete]` 按钮等）。comic 侧因为有 `sampleImgPixels` 像素采样，反而更可靠。**待办：给连线补一条「像素级可见性」断言**（截图后在曲线中点采样，断言非背景色）。

- A 最小改动：把 `.svg` 尺寸改成非零（如 `1px×1px`）——2 行 CSS，实验已验证有效，但依赖 `overflow:visible` 溢出绘制这一「隐式行为」。

## 陈旧标记 + 按范围重跑入口（对账清单缺口 1+2 合并打掉，#174–#178）

**为什么合并成一组**：两者都是「引擎 / 模型已就绪、只差一层皮」的同类洞，且**互相依赖**——「仅刷新陈旧」模式要先有陈旧标记才有意义，陈旧标记又要靠重跑来消除。分两轮做会先交付一个「标了但没法重跑」的半成品。

### 台账记错了：陈旧标记不只是「没渲染」

对账清单原记「字段 / 类型 / 传参全有，只是 `NodeFrame` 不消费」。读代码后发现更深：**`stale.mark` / `stale.clear` 命令在生产代码中从未被派发**（只在 `reducer.test.ts` / `store.test.ts` 里出现过），`useExecution.onFinish` 的注释写着「补发 `stale.clear`」而实现只做了 `store.flush()`。⇒ **连「何时该变陈旧」都没有人在算**。必须把计算与渲染两端一起补，只补渲染仍是死的。

### 陈旧判定：一条式子 + 「无基线不表态」

- 纯函数 `domain/canvas/staleness/staleNodes.ts` 的 `staleReport(graph, liveFingerprints) → { stale, fresh }`。
- 判定**只有一条**：`当前指纹（fingerprintOf(节点, 上游输入)）≠ 最近一次成功生成的指纹`。同时覆盖「上游产物变了」（上游 `assetHash` 进下游输入摘要）与「自己参数改了」，**不需要分别追踪**。
- **无基线（从未成功生成）刻意两边都不进**：标陈旧是假信号（空节点本来就要跑），当成新鲜则会抹掉「导入时模型缺失」自带的陈旧。

### 清除判据：「可证明」而非「我记得」

第一版用 `markedRef: Set`（「本层标过谁」）决定 clear——**刷新即丢**。改成 `fresh` 集合（有基线且当前指纹 = 基线）：**只有能证明已回到基线才清**。理由：`「不在陈旧里」不构成清除理由`，因为无基线的节点也不在陈旧里；若写成「不在 stale 就 clear」，导入态的 stale 会被无声抹掉。`fresh` 每次都能重算，不依赖任何会话内记忆。

手动清除仍留豁免（记「清除那一刻的指纹」，指纹再变即失效重标）——**豁免基于指纹而非布尔，故刷新后依然正确**。

### 接线落点（顺带修正架构文档）

架构文档原设计 `state/workbenches/canvas/staleSlice.ts` + `features/canvas/staleness/useStaleness.ts`——**两者都不存在，且不该存在**：判定的**基线来自 `RunRecord`**（version 最大且 `succeeded` 那条），而 RunRecord 的写入 / 版本计数 / 「引擎之外的写入方」（版本恢复 `appendRecord`）都在**执行宿主**这一层。另起一个 hook 只会逼出第二份基线来源（谁记、谁同步、刷新后谁重建）。⇒ 对账落在 `CanvasExecutionProvider`，架构 §4.4 已改为实际落点并写明理由。

`writeBack` 里 `noteRecord` 必须**同步**记账（不能靠 React 批处理，否则本帧对账拿旧基线比对）。

### 按范围重跑：引擎早已全备，补三层皮

- 引擎：`buildRunPlan` 支持无 origin 的**全图** `refreshStale` / `rerunAll`；`canBuildRequest` 由私有改导出（供右键菜单判「下游是否真有可执行项」，避免列出点了没反应的死项）。

### 顺手修掉一个真缺陷：刷新后重复套用模板

### 症状与根因（两条症状同源）

1. **工作区顶栏零导航出口**。`/settings` 的唯一入口一直在**首页顶栏**（`HomePage.tsx:124`）；进了画布就断了——顶栏只有画布内操作按钮（＋提示词/对比/分组/批量/撤销/重做/复位视图/日志/仅刷新陈旧/全图重跑），**连「返回首页」都没有**，只能靠浏览器后退键离开。漫画页有「← 返回」但同样没有后台设置（两页不对称）。
2. **空渠道无引导**。渠道是生成的**硬前置**（`enabledChannels()` 只返回 `enabled===true`），空渠道下平台下拉**没项可列**却只是一个空下拉，不解释不引导；用户点生成毫无反应。模板项目的 `channelId` 为空 ⇒ 新建即无渠道。

**两条合起来 = 用户口中的「生不出图」**：链路断在「没有渠道」，不是模型没接。

### 修法（三处，均不破架构边界）

- **顶栏补出口**：画布 / 漫画 `CanvasTopBar` 在 brand 后各加 `← 返回`（`data-topbar-back`）+ `后台设置`（`data-topbar-settings`），中间一条 **1px 分隔线**隔开「离开工作区」与「工作台内操作」两族按钮。`后台设置` 带 `title` 说明前置条件。
- **空渠道引导**：生成节点平台下拉在无可用渠道时换成按钮「去配置平台」（`data-node-setup-hint`）；创作面板同位置显示引导条（`data-panel-setup-hint`），**文案二态**：`还没有配置任何渠道` / `已配置的渠道都未启用`。订阅 `channels` store（`useSyncExternalStore`），设置页改完即时反映。
- **设置页按来源返回**：读 `location.state.from`，`backTo` / `backLabel` 按来源切换（← 返回画布 / 漫画剧 / 首页，`data-settings-back`）。

### 架构边界（本轮最要紧的纪律）

工作台 UI 层**不认识路由**（架构 §4.7）。节点 / 面板**不 `useNavigate`**，而是 emit **宿主导航语义事件**：`PanelEvent` 与 `NodeViewEvent` 各加 `{ type: 'openSettings' }`。透传链：
`GenerationNodeView` / `CreationPanel` → `PanelLayer` / `NodeLayer` → `CanvasSurface` → `CanvasPage`（`useNavigate` 翻译成 `navigate('/settings', { state: { from } })`）。`workbenches/` 里**不出现 `react-router`**。架构文档 §4.7 已补这一段。

### 教训沉淀

## OpenAI 兼容协议：接真实中转时暴露的生图参数与地址缺陷（用户给 `gpt-best.apifox.cn` 让我「配置这个协议」）

### 定性（先说结论）

`gpt-best.apifox.cn` 自查文档原文：**完全对齐 OpenAI 官方**，用法 = 把 `api.openai.com` 换成它的 Base URL，Key 放 `Authorization: Bearer sk-xxx`。⇒ **不需要新建协议**（为一个厂商新建「协议」是把厂商当协议，架构上错）；应用里已有「OpenAI 兼容 · 生图」即为对接方式。所以本轮做的不是「加协议」，而是**让这个已有协议在真实中转上真能用**。

### 四个缺陷（`mock` 协议下永远不暴露）

| # | 缺陷 | 后果 |
|---|---|---|
| ① | 适配器无条件拼 `${base}/v1/...`，而中转地址**可能带也可能不带 `/v1`** | 地址含 `/v1` → `/v1/v1/models`，**一律 404**；报错只说「端点不存在」，用户猜不到是自己多贴了一段 |
| ② | `size` 由 `ratio.replace(':','x')` 生成 → 发 `"1x1"` | OpenAI 规范要**像素**（`1024x1024` / `1536x1024` / `1024x1536`），`"1x1"` 非法，真实模型拒绝 |
| ③ | `quality` 参数面板一直在、**从没被发出去** | 质量档位形同虚设 |
| ④ | 产物 `width/height` 写死 `512` | 与真实产物无关的假值 |

**根因（最有价值的一条）**：适配器**只对着 `mock` 协议联调过**——mock 不看 `size` / `quality`、也不校验地址形状 ⇒ **假数据把整类缺陷挡在视野外**。与 M6-9 那条「假字节 + 真 mime 是最危险的假数据」同源：**假数据的保真度决定断言的上限**。

### 修法（纯函数 + 真实请求体断言）

- `normalizeBaseUrl(raw)`：剥结尾版本段 + 斜杠（`https://x/v1` → `https://x`），再由适配器补一次 `/v1`，两种写法都成立。
- `openAiImageSize(ratio)`：比例→像素；**表外比例返 `null` ⇒ 不发 `size`**（宁用服务端默认，不猜）。
- `openAiImageQuality(q)`：只放行 `auto` / `low` / `medium` / `high`，其余不发（发了就是 400）。
- **`resolution`（1K/2K/4K）刻意不发**：OpenAI 图像协议**没有档位参数**；把 2K 猜成 `2048x2048` 在多数中转上直接 400，比「档位不生效」更糟。如实写进产品文档 §11.1。
- 产物宽高**取自请求的 `size`**，解不出就不写（不再编造 512）。
- 设置页地址占位符补「（含 /v1 或不含都可以）」。

### 冒烟为什么不覆盖它

`scripts/smoke.mjs` 全程走 `mock` 协议，**零处**触及 `images/generations`。故本轮保障**全在单测**：`openaiImages.test.ts` **17 项（+8）**——归一分 4（含「地址已含 /v1 时不得出现 `/v1/v1`」）、size 映射 3（含「未知比例不发 size」）、quality 1；四类断言都直接查**真实请求体 / URL**。

**通则（已写进对账清单 §七）**：协议适配器不能只有 `mock` 一个联调对象，每条参数映射都该有一条断言真实请求体的单测。

## 收口 · 设置页「验证地址」走不到所选协议（用户截图反馈）

### 现象（用户原话 + 截图证据）

「验证地址的时候无法到我兼容的协议，先把目前我要的那个协议配置好先」。截图：协议下拉仍是 **`Mock（离线验证）`**、地址框有值、状态行 `✓ 验证通过，发现 2 个模型`（= mock 的两个内置假模型 `mock-image-1` / `mock-chat-1`）⇒ **一个网络请求都没发**。

### 根因（两层，都在「表单态 vs 落库态」这个缝里）

| # | 根因 | 表现 |
|---|---|---|
| ① | `channelStore.verify(id)` 读的是 **`repo.get(id)` 里已保存的 `protocol`**（`toSafeConfig(ch)`），而协议下拉只是**表单态**，不点「保存配置」就没落库 | 「把协议切到 OpenAI 兼容 → 直接点验证地址」时，**切了协议这件事在验证那一刻并不存在**，走的还是 mock ⇒ 秒过 + 2 个假模型 |
| ② | 验证成功会回写 `modelCache`（`repo.update`）⇒ `channels` 数组换新 ⇒ `selected` 换新；而表单同步 effect 原先**依赖整个 `selected`** | 后台更新把用户的**未保存编辑静默覆盖**：刚选好的协议自己**弹回 Mock**，看起来像「选不上 / 选了又跳回去」 |

顺带发现两个同源的展示缺陷：
- **`✗ [object Object]`**：`classifyError` 只认 `instanceof Error`，而网络端口抛的是**归一化 `AppError` 字面量**（`throw {kind:'network',detail:'dns'}`）、渠道层抛 `ChannelError`（载荷在 `appError` 上）⇒ 掉到 `String(e)`。
- **「拉取模型」零反馈**：`refreshModels` **没有 catch**，地址错时抛成未捕获拒绝，用户点了按钮什么反应都没有。

### 修法

1. **「验证地址」「拉取模型」先落库再发请求**（抽出 `persistForm()`，`syncForm(saved)` 回写表单以库为准）——**所见即所验**。顺序语义由按钮承担，不靠用户猜。
2. **表单同步只在 `selectedId` 变化时发生**（改为在 effect 内 `channels.getState().channels.find(...)` 取值，dep 只留 `selectedId` + `channels`）——不跟 store 的后台更新走。副作用：启用开关的即时写盘也不再冲掉未保存的名称/地址。
3. **状态行标注协议名**：`✓ 验证通过 · OpenAI 兼容 · 生图 · 发现 12 个模型`（按动作分叉「已拉取模型」/「验证通过」）；`verifiedFor = {channelId, protocol, source}` 让状态行只对**当前选中渠道 + 最近一次动作**负责（store 里的 `verify` 是全局单份，否则 A 渠道的结论会挂到 B 头上）。
4. **mock 通过时给显式离线提示**（`data-settings-mock-note`）：mock 是离线协议、不发任何网络请求、也不访问所填地址，返回内置假模型；要联调真实中转把协议切过去。
5. **`shared/result` 新增 `asAppError(e)`**：裸 AppError 字面量 / `ChannelError.appError` 两种形态统一取出。`openaiImages` 用它 + `appErrorMessage/h httpMessage` 映射可读文案（`连不上这个地址（域名解析失败或连接被拒绝）——核对地址、确认中继可达`）；`channelStore` 两处 catch 一并改用它（顺带不再泄漏 `[channel] unsupported`）。
6. `refreshModels` 补 catch，与 verify 共用同一条状态行（含 `checking` 态）。
7. 设置页加 `data-settings-protocol` / `data-settings-baseurl` 便于稳定选择器。

### 回归

- 新增冒烟 **G43「协议切换即生效」10/10**（双向有效：修复前那两条会红）。死地址用 **`127.0.0.1:9`**（discard 端口，必然拒绝连接）——让「出没出网」有**确定性判据**（本地行为，不依赖 DNS / 外网），而不用不可达域名。三段：A mock 基线自曝协议 + 离线提示 → B 不点保存直接验证**必须失败**、协议**不被弹回** → C 刷新后协议与地址都已落库。
- 单测新增 `shared/result.test.ts`（4 项：裸字面量 / 带货 Error / 普通 Error 与畸形容器返 null / `describeError` 全 kind 不落空）+ `openaiImages.test.ts` 失败文案 4 项（AppError 字面量 / HTTP 状态 / `ChannelError` 载荷 / 404 响应，断言**不含** `[object Object]` 与 `[channel]`）。

## 收口 · 设置页 §7.2/§7.3/§7.4 补齐（模型管理闭环 + 排序 + 令牌）

### 起点：用户原话「我的后台模型页的功能好像没有实现完成」

核对后确认**不是「没做完」，是「根本没做」**——产品文档 §7.4「模型管理」整节零落点：拉回来的模型**直接等于**渠道可用模型，无选择面板、无「已选」概念。于是真实中转拉回 40+ 模型 → 画布/漫画模型下拉就列 40+ 个，用户**没有任何筛选手段**。

**同时暴露口径问题**：文档 §7 各节按草案**先声明 ✅**，代码却停在 M2 一次性实现上。**「文档标 ✅」与「功能真存在」之间没有核对动作** → 缺口被文档掩盖了几个里程碑。此为**对账清单第四条通则：声明即负债**（见下）。

### 数据模型（骨架，本组关键决定）

| 字段 | 语义 | 落点 |
|---|---|---|
| `modelCache` | **拉回来的全部**（只喂选择面板、供勾选） | 保留旧字段 |
| `models` | **用户勾选的**（画布/漫画下拉**只读这份**） | 新增 |
| `order` | 列表排序（不进 Dexie 索引，`list()` 内内存排） | 新增，`schemaVersion` **不升** |
| `lastTestAt` / `lastTestLatency` | 验证时刻与墙钟耗时（含 DNS/TLS/响应体） | 新增 |
| `tokenTail` | 令牌末 4 位（明文唯一一次在手时截取；<12 位不给） | 新增 |

`SUPPORTED_PROTOCOLS` 加 `short`（`mock→MOCK`、`openai-images→OAI`）+ `protocolShort()` / `tokenTailOf()` / `maskTokenTail()`。

### §7.4 选择面板（草稿态 + 两条应用规则）

- **草稿态**：面板内勾选先存 `draftChecked`，点「应用」才 `setModels`。**草稿态的意义是不让半途勾选污染生成链路**（中途反悔关掉，已选一个没变）。
- **分类（全部/生图/对话/视频，三组固定顺序、空组保留）+ 关键字过滤（与分类是「与」、保持输入顺序）**。
- **应用两规则**（纯函数 `domain/project/modelSelection.ts`，**单独成模块 + 单测**，因「界面上看不出对错」）：
  - ① **命中缓存以缓存为准**（候选的能力参数随拉取更新会覆盖旧快照）；
  - ② **缓存消失但仍勾着的保留**（上游临时改名/少回一个模型，不静默清用户的选择）。
- **验证不替用户勾选**：`verify` 通过**只写 `modelCache`**、绝不写 `models`。此前「验证通过顺带全选」是**替用户做了他没做的决定**，而「拉回 40 个只想要 2 个」时这个默认恰恰是错的。
- **三空态文案各不相同**：`还没有验证过…` / `拉取到 N 个模型，但还没有勾选` / `该平台没有返回模型`。
- **下游空态给出口**：渠道启用但 `models` 空 → 节点/面板显示 `去选模型` / `该渠道还没勾选模型`，点击直达设置页。

## 设置页改版（用户三点诉求：居中卡片 / 验证协议 / 删不掉）

## 生成节点未按文档制作（用户指出）——节点本体 vs 创作参数面板「两套并存」

**用户判词**：「生成节点没有按照我的文档进行制作」。真机探针 `scripts/probe-gen-node.mjs`（12 项，**9 失 3 过**）+ 逐行读码，确认是**结构性偏差**，不是细节：

## 画布：生成节点本体按文档重塑为「媒体框」+ 标题移出节点外（用户「确认」后落地）

**起点**：用户判词「生成节点没有按照我的文档进行制作」→ 诊断（上一段 §⑨⑩）确认为**结构性偏差**：节点本体又把创作面板的东西画了一遍（平台/模型下拉 + 提示词框 + 生成按钮），于是本体失去「媒体框」身份。用户「确认」后按 §6.8 / §6.6 重塑。

### 关键设计判断

1. **减重而非加壳**：本体瘦成媒体框后，孤儿文件 `Placeholder.module.css` 的语义才落地；参数 / 提示词 / 生成按钮**只有一个家**（创作面板）。
2. **占位框本身不是按钮**：只有中间 `＋` 是上传入口——否则点节点任意处都弹上传、且**无法拖动节点**（框是拖动把手，§6.15）。
3. **标题浮出后 `HEADER_H` 必须删**：`NodeLayer` 原按 `h - 32` 给节点算内容高；标题移出后节点框**整体即内容区**，再减 32 就少 32px。删掉后内容区与文档 §6.16 尺寸一致。
4. **容器子节点不渲染标题**（`!inContainer`）：容器内是 16px 间隙网格，浮标题会压到上一行、且被 `overflow:hidden` 裁掉；子节点身份由内容表达。
5. **上传三件事全在宿主侧**（视图拿不到 `FilePort`、不算哈希、不派发命令，架构 §4.7）：取文件（`pickFile` 或拖入的 `file`）→ `fingerprintBytes` 算**内容哈希**（与生成产物同口径 ⇒ 同图重传天然去重）→ `asset.put` 落 `assets` + `node.updateData({assetHash})`。图片补 `naturalSize`（供锁比例），视频尺寸留给解码。
6. **`requestUpload` 的 `file?` 可选**：点 `＋`（无 file → 宿主开选择器）与拖入（带 file）**汇到同一段落库逻辑**，不写两套。
7. **删自身素材返 `undefined` 而非删键**：全站判断走真值、JSON 落库自然丢弃。只有 `owner==='self'` 的项给 `✕`；**上游缩略图只给小眼睛**（取消连线才移除）。
8. **「重置视图」统一为 `fitCanvasView`**：`Z` / 工具栏 / 空白右键原写死 `{0,0,1}`，与 §6.3「缩放至全部节点可见」不符 → 三处共用一份（含顶栏/左工具栏浮层避让边距 72；只统计顶层节点）；模板播种后也自动适配一次。

### 通则（NEW）

**⑪ 「同一个功能有两套 UI」的修法是「减重」，不是「给旧的那套加壳」。** 发现节点本体与面板重复时，第一反应若是「把节点里的控件也接上逻辑」，就把化石层固化了；正确动作是**按文档定义删掉节点里不该有的东西**（本体 = 媒体框），让每个功能只有一个家。删完顺带要扫「**因减重而失效的常量**」——本例 `HEADER_H`（按「标题占 32px」写死）在标题移出后就成了错误的高度补偿，不改就会少 32px。
**⑫ 可拖动把手内的文字必须 `user-select:none`。** 凡「整块区域可拖动 + 内含可选文字」的组件，按下文字拖动都会触发**原生文本拖拽**（`dragstart` → `pointercancel`），掐断自定义指针拖拽的 `pointermove`/`pointerup` 流，表现为「只挪第一拍就停、松手不结算」。判据：**捕获事件流看有没有 `pointerup`**——没有就是被原生拖拽吃了。修法两道（源头 `user-select:none` + `onDragStart` preventDefault）。

## 补记 · 生成节点内部底色 + 数量胶囊可用性（用户报「有些参数点不动」）

**用户原话**：「生成节点得内部颜色需要和提示词节点得内部颜色一样，参数得设计我记得是上拉得面板吧，有些参数还动不了点不动」。用两个真机探针（`probe-params.mjs` / `probe-video.mjs`）逐条核对：①底色不一致 = **真缺陷**；②面板形态 = **用户记错**（文档定义就是「节点下方浮动面板」）；③参数点不动 = **真缺陷，两处**。

### ① 媒体框底色回归（`70e26a2` 顺手引入）

提示词节点 `.body` **不设底色** → 透出 `.frame` 的 `--bg-surface`（白）；生成节点 `.media` 写了 `--bg-subtle`（`#f7f7f8` 灰）。真机采样 `rgb(247,247,248)` vs `rgb(255,255,255)`，同屏并排肉眼可见。**重塑前本体根本没有底色**，是重塑时加的 ⇒ 回归。修法：`.media` → `var(--bg-surface)`；§3.3 补通则「节点内部一律白底，不靠底色差区分」。修复后两节点均 `rgb(255,255,255)`。

### ② 数量胶囊 2张/4张/9张 整排置灰

`maxCount = Math.max(1, activeModel?.maxCount ?? 1)` 的 `?? 1` 把「还没选模型」与「模型没上报 `maxCount`」都判成「最多 1 张」→ 一进面板 2/4/9 全 `disabled`，title 还是**假话**「当前模型最多 1 张」。**多数中转渠道的 `/v1/models` 不报该字段 ⇒ 接真实渠道时恒定只剩 1张 可点**（§6.8「固定四项」压成一项）。修法：**未声明 = 不设限**（上限取最大档位 9），只有模型显式声明更小上限才置灰够不到的档位。`CreationPanel.test.ts` +3 条（未选模型 / 未声明 / 声明 4 才置灰）。修复后四档全可点；选中 mock（`maxCount:4`）后**仅** 9张 置灰。

### ③ 面板形态（回答用户疑问，未改代码）

§6.8 原文「**位置 = 始终在节点下方，水平中心与节点对齐，拖动跟随**」；真机几何实测吻合（节点下沿 y=528 → 面板上沿 y=540，宽 840px、高自适应）。**是节点下方浮动面板，不是上拉 / 抽屉面板**。要改成上拉属改设计，须先改文档再改实现。

### 通则（NEW）

**⑬ 重塑节点结构时「顺手新增的装饰性底色」是回归的高频来源。** 重塑前本体没有底色，是重塑时加的 `--bg-subtle` ⇒ 同屏两种底色。凡给节点内部新增填充色，先问一句「另一个节点内部是什么色」。
