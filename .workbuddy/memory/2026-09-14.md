## 上传卡顿诊断（用户提问：「图片上传进去的时候会很卡，是文件太大了吗？」）

**结论：一半是，一半不是。**

三条独立瓶颈（探针实测，见下表）：

1. **固定约 1050ms 空窗（与文件大小无关，人人都中）** —— `useAsset` 只查 IndexedDB，而 `asset.put` 先进内存图、靠 **800ms 防抖**才落库 ⇒ 上传后必然 miss，靠 `useAsset` 的 250ms 退避重试兜底 ⇒ 800 + 250 ≈ 1050ms 才出图。**0.14MB 的 800×600 也要 1067ms**，其中真正干活（读字节 1ms + 解码 5ms + 落库 3ms）只有 9ms。用户感知就是「点了上传，半天没反应」。
2. **同步 SHA-1 阻塞主线程（大图才明显）** —— `sha1Bytes` 纯 JS 同步（约 30MB/s），对全部字节跑 ⇒ 3.5MB 阻塞 120ms、7MB 阻塞 187ms，期间 UI 完全无响应。**这才是真正「卡」（鼠标划不动）。**
3. **`readImageSize` 用 `createImageBitmap` 全量解码只为取宽高** —— 6000×4000 → 114ms + 约 96MB 位图峰值。取宽高本可读文件头（PNG IHDR / JPEG SOF）。

**已证伪的怀疑（别再往这查）**：拖动 / 缩放 / 平移**不会**让 `useAsset` 重建 blob —— `createObjectURL` 增量 0，帧间隔 p50=6ms、零掉帧。原因是 `useSyncGraph` 的 tick 只在 graph 变化时 +1，而 selection / viewport 不在 graph 里。第一版探针用「点空白 / 平移」去测，测出来 +0 差点误判为「没这问题」。

**实测数据（端到端 = drop → 新图真正解码完成）**

| 尺寸 | 体积 | 端到端 | 读字节 | 主线程阻塞 | 解码 | 落库 |
|---|---|---|---|---|---|---|
| 800×600 | 0.14MB | 1067ms | 1ms | 0 | 5ms | 3ms |
| 1600×1200 | 0.56MB | 1055ms | 1ms | 0 | 10ms | 14ms |
| 2400×1600 | 1.13MB | 1083ms | 1ms | 0 | 19ms | 23ms |
| 4000×3000 | 3.53MB | 1190ms | 2ms | **120ms** | 57ms | 77ms |
| 6000×4000 | 7.05MB | 1362ms | 6ms | **187ms** | 114ms | 140ms |

**探针方法（可复用）**：`addInitScript` 里 patch `Blob.prototype.arrayBuffer` / `createImageBitmap` / `IDBObjectStore.prototype.put` / `URL.createObjectURL` 计时计数，配 `PerformanceObserver({entryTypes:['longtask']})` 抓主线程阻塞，再挂 rAF 采样帧间隔算 p50/p90/janky。

**★ 探针陷阱**：等待条件必须是「**新增的那张**解码完成」，不能写「存在任意 `img`」—— 上一张还在页面上，第一次检测就命中，后面所有样本都是假数据（第一版就是这么废掉的，5 组数据里 4 组是 5ms 的假象）。判据：同时打印节点数 `n0→nNow` 确认每张都真的进来了。

## M6-26 上传即显（对账清单 #15，已交付）

用户实测报「图片上传进去的时候会变得很卡，等好几秒他都没上传上去、没显示」。**不是「文件太大」一个原因**，探针实测拆出三处叠加瓶颈，逐个拆掉：

1. **`assets` 表插队立即落库（不等 800ms 防抖）** —— `useAsset` 只认 IndexedDB，素材跟着防抖走 ⇒ 上传后固定空窗；更糟的是重试窗口原本只有 12×250ms=3s，**多张连传时主线程被占、防抖计时器被推迟 ⇒ 落库晚于 3s ⇒ 永久空白**。这是**显示失败不是慢**。改 `URGENT_TABLES={assets}` 命中即 `flush()`；冲刷改**串行链**防交错丢写。其余表仍走防抖。
2. **`fingerprintBytes` 改异步**：优先 `crypto.subtle.digest`（原生线程，7MB 实测 4ms），无 `crypto.subtle` 回落纯 JS `sha1Bytes`。原同步实现对全部字节跑 80 轮：7MB 阻塞主线程 233ms。**两条路径哈希值一致**（固定向量单测钉住），否则同图存两行、内容寻址失效。两个调用方（`importAsset.ts` / `characterRefUpload.ts`）随之改 `await`。
3. **宽高读文件头**：新增 `domain/shared/imageSize.ts#imageSizeFromHeader`（PNG IHDR / JPEG SOF / GIF / WebP VP8·VP8L·VP8X，零解码）；读不出才回落 `createImageBitmap` 全量解码，**绝不猜尺寸**。
4. 兜底：`useAsset` 重试窗口 3s → 约 20s（前 3s 每 250ms、其后 500ms，上限 48 次），且图一变就重跑 effect 归零计数 ⇒ 不存在「重试完就永久空白」。

**效果**（同一张 5.4MB 不可压缩 PNG，应用侧时钟）：端到端 **1067ms → 230ms**；最长长任务 **728 → 62ms**；`createImageBitmap` 1 → 0；连传 3 张全可见。

**两条提前拆掉的坑（纯数学，写错就会在交互上放大）**：

1. **范围只由内容决定**（顶层节点 + 结果组；无内容才退化为视口）。若把视口并进范围，一边拖一边改视口会反过来改 `scale`，同一个光标位置映射到的世界坐标**越拖越远**——自我放大的回路。范围与视口无关，映射恒定，拖拽天然稳定。
2. **视口框越界「保尺寸、挪位置」钉回框内**（比框还大时铺满整框）。用「求交」会让框变小、被读成「看得更少了」，而它真正的含义是「已经偏出去了」。

**画谁**：只画顶层节点与结果组——容器内子节点的 x/y 是局部坐标，混进来拉偏范围（与 `fitCanvasView` / 框选命中同一口径）。
