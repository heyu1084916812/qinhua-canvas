# CanvasFlow（轻画）项目记忆

### ★ 参考素材：Agnes **收 Data URI**，图床只是可选加速（2026-10-03）

用户要求「图片节点和视频节点按每个模型单独配参数」+「单独做一个图床设置页」时，
把两件事都真打了一遍接口（对账清单 #114–#117）。**最重要的一条是推翻了自己先前的判断**：

- 我们此前在代码里写死「参考图 / 首尾帧需要公网 URL，浏览器里的本地素材传不上去」，
  并**主动拦住**带参考图的请求。实测：`agnes-video-v2.0` 的 `mode:'keyframes'`
  **收 `image:["data:image/png;base64,…","…"]`**（HTTP 200 正常排队），
  图片接口文档也明写 `image` 支持「public URLs **or Data URI Base64**」。
  ⇒ **本地素材根本不用先上图床**。（教训：文档里的「必须公网 URL」要**亲手验一次**再写进代码当门禁。）
- 2.0 的参考参数名是 **`image`（数组）**，不是 2.5 文档里的 `first_frame`/`last_frame`/`images`；
  `keyframes` 要求**至少 2 项**（错误原文：`mode=keyframes requires image as a list of at least 2 items`）。
- **图床候选实测（都在应用 origin 的浏览器里真发）**：freeimage.host / catbox / uguu / qu.ax /
  envs.sh / file.io / 0x0.st 全 `Failed to fetch`；pixeldrain 要 API key；litterbox `412`；
  **只有 tmpfiles.org 成**。它的两个坑：返回的是**页面地址**（直链要换 `/dl/`），
  默认 **60 分钟**删除（上传可带 `expire`：3600/21600/86400/172800）。
- **免费档限流很紧**：连着发几次视频请求就 `429 rate limit for free users`。探针要**一次问一件事**、
  中间留间隔，否则后面的探针全是 429，看起来像「参数不被支持」。

### ★ 每个模型自己的参数：别用一套通用档位（2026-10-03）

- **图片**：Agnes Image **2.0 = 像素**（`1024x768` 这种，没有 `ratio`），
  **2.1 / 2.5 = 档位**（`1K–4K` + 8 档 `ratio`）；三者**都没有 `n` 和 `quality`**
  —— 面板摆出来就是死格子，适配器发了就是换 400。
- **视频**：同一个 host 上 **2.0 与 2.5 是两套形态**（对账 #112）。2.0 收下档位参数却**无视**它
  （回填默认 `1088x832`），只认**像素 + 帧数**；所以按 `dialect` 分家决定先发哪套。
- **中转站那一侧又是另一套**（Comfy-gpt 实测，对账 #118）：`gpt-image-2.5-flare` / `-sunburst`
  的 `size` **必须是 `WxH` 像素**（传档位字符串 → 原话 `size must be in WxH pixels format`），
  `quality` 合法值是 **`auto / low / medium / high / xhigh / max`**（比 OpenAI 多两档，
  我们此前只放行四档、把 `xhigh`/`max` 静默吞了）；`gemini-3-pro-image`（Nano Banana Pro）
  **在这条 relay 上不吃 `/v1/images/generations`**（503「不支持此 API 路径」），
  而 `gemini-3.1-flash-image` 能出图但**把 `size` 与 `aspect_ratio` 都忽略**（对账 #119）。
  ⇒ **同一个模型名在不同站点是不同协议**，参数表只能按站点实测，别照抄官方文档。
- 非 Agnes 的固定显示名**只写实测过的**：Comfy-gpt 的三个 GPT Image 档（方言
  `openai-images`：官方 `size`（`auto`/`1024x1024`/`1536x1024`/`1024x1536`）+ 六档 `quality`
  + `n` 1–10）与 **Nano Banana 两个**（方言 `gemini`：走 **Gemini 原生端点**
  `/v1beta/models/<id>:generateContent` + `imageConfig.aspectRatio/imageSize` ——
  官方 14 档宽高比、`1K/2K/4K`（Flash 多 512）；`/images/generations` 对 Pro 是 503，
  chat 路径会把这两个参数**吃掉**）都已写进 `imageParams.ts`。
  **官方文档怎么拿到**（Node 直连大多不行）：OpenAI / Midjourney 的站点 403（Cloudflare），
  Google 站点在 Node 侧连接超时 —— 要**用系统 Chrome（走代理）**打开才能读；
  OpenAI 的参数最好直接读它的**官方 OpenAPI 规范**（`raw.githubusercontent.com/openai/openai-openapi`
  的 `CreateImageRequest`，一次 3.9MB，字段与枚举齐全、不依赖页面渲染）。
  MiniMax 文档是 JS 壳（正文 46 字符）、Midjourney docs 403 ⇒ 这两家本轮没拿到正文，
  对应模型仍按渠道上报的能力渲染，不凭猜写死（对账 #119 / #120）。
- 一句话教训：**「发出去没报错」不等于「生效」** —— 判据要看响应回填的字段（尺寸 / 模式），
  不是只看 200。

### ★ 远端素材（视频成片）下载：本地没字节 ≠ 素材不存在（2026-10-03）

用户报「刚刚生成的视频，只有双击进灯箱才能看，节点的下载功能无法下载，显示素材不在素材库」
（对账 #110 / #111）。两条根因，形状是同一种错误：**拿一个代理指标当真相**。

1. **下载链路只认 `assets.bytes`**：Agnes 成片托管域没有 CORS 头（页面里 `fetch` 一律
   `net::ERR_FAILED`），落到库里的那一行只有 `url`、字节是空的 ⇒ 读字节失败被判成
   `missing`，提示就成了「这张素材已不在素材库里」。**判据得分两层**：先问字节、再问地址，
   两者都没有才是真的没有。修法：`AssetPort.readUrl`（地址 + 类型单开一口）+
   `FilePort.saveFromUrl`（取得到字节就真落盘，取不到就把地址交回浏览器）。
2. **节点用 `data.mode` 决定渲染哪套标签，灯箱用 `assets.mime`** ⇒ 两边结论不一致时，
   节点会拿 `<img>` 去显示 mp4（一块空白），双击进灯箱反而正常。**「这到底是什么」全应用
   只该有一处判据**：以素材行的 mime 为准，拿不到 mime 才退回节点自己的 mode。

**两条浏览器实测出来的硬事实**（都别凭直觉）：

- **跨域 `<a download>` 的 `download` 属性会被忽略**：Chromium 里裸点等于**导航** ——
  本机实测当前页直接跳到视频地址（画布就没了）。做兜底必须 `target="_blank"`。
  判定手段：Playwright 的 `waitForEvent('download')` 收不到，而 `page.url()` 变成了目标地址。
- **同源 fetch 的「失败」要看清楚**：Vite dev server 对未知路径回 **index.html 200**
  （SPA fallback）⇒ 用「本地不存在的一个路径」模拟「取不到字节」是**测不出来**的，
  那一版冒烟就是因此假绿。要模拟不可达，用 RFC 2606 的 `.invalid` 主机
  （或 `ctx.route()` 显式 abort），别用同源路径。

**验证**：单测 1466/1466、`npm run check` 全绿、冒烟 **G96 9/9**、**全量冒烟 1035/1035**（新增组：种一条
「只有 url、没有字节」的素材 + 引用它的节点，分别验「取得到字节 → 真下载」「取不到 →
新标签页 + 正确提示」，并把节点渲染成 `<video>` 钉住）。

### ★ Agnes Video 参数口径速查（2026-10-03，官方文档原文比对）

- **2.5 与 2.5 Flash 是同一套接口**；Flash 只有四种硬差别：`size` 只能 `"720P"`、
  `images` ≤5、`audios` ≤3、**不支持 `videos`**（传了回 400）。
- **公共参数**：`mode` = `text` / `keyframe` / `reference`；`seconds` 是**字符串**
  `"4"`–`"12"`；`size` = `720P` / `1080P` / `1K`（固定 1024×1024）/ `2K`；
  `aspect_ratio` 六档（21:9 / 16:9 / 4:3 / 1:1 / 3:4 / 9:16）；`seed` 可选；`n` 只能 1。
- **参考类参数全是公网 URL**：`first_frame` / `last_frame` / `images[]` / `audios[]` /
  `videos[].url`，且文档明写「媒体链接须公开可访问、任务完成前保持有效」⇒ 本地字节
  必须先有公网地址（图床 / 后端中转），这就是 #106 / #113 的前置条件。
- **2.0 与 2.5 是两套词表 —— 实机实测（2026-10-03，真令牌直打 `apihub.agnes-ai.com`）**：
  `mode` 的服务端枚举 = `ti2vid` / `keyframes` / `multi_reference`（发别的 400 原话：
  `Input should be 'ti2vid', 'keyframes' or 'multi_reference'`）；给 2.0 发
  `size:"720P" + aspect_ratio:"16:9"` **HTTP 200 却不生效**，排队回填的是默认
  `1088x832`；发像素那套（`width` / `height` / `num_frames` / `frame_rate`，**不带 mode**）
  回填 `1280x704`、时长按帧数算 ⇒ **2.0 = 像素形态，2.5 = 档位形态**（#112）。
  **教训：参数「发出去没报错」不等于「生效」** —— 200 的响应里可能已经把你选的尺寸丢掉，
  判据要看**响应回填的 `size`**，不是只看状态码。
- **发送顺序**由 `VideoParamSpec.dialect` 决定（2.0 = `pixel` 先发像素、2.5 / Flash = `tier`
  先发档位），另一套留作 400 回落；谁把顺序调回去，`openaiVideo.test.ts` 里那三条会红。
- 带 `seed` 的像素形态请求被接受并正常出片（是否真的影响结果未验证）；免费档连发几次就
  `429 rate limit for free users`，别用连发的方式做探针。

### ★ 图床能不能用，卡在 CORS 与「直链是不是真图片」（2026-10-03）

用户问「第三方临时图床有哪些」，我拿一张 246B 的纯色 PNG 真传了一遍（对账清单 #108）。
**教训是：光看「有没有 API、保留期多久」选不出能用的图床，真正的门槛是两条，
而且两条都不写在对方的宣传页上。**

1. **CORS**：轻画现在是浏览器应用，页面 `fetch()` 跨域 POST 到图床，**响应必须带
   `Access-Control-Allow-Origin`**，否则浏览器会拦掉「读返回值」这一步 —— 文件其实传上去了，
   但应用拿不到 URL，体验上就是失败。实测：`uguu.se` / `temp.sh` 上传都回 200，
   但**都没有 CORS**；`imgbb` 有（`ACAO: *` + 预检 200），`litterbox` 也有，但它另一个问题。
2. **直链是不是真的返回图片字节**：`temp.sh` 上传成功、返回的 URL 看着像图片
   （`https://temp.sh/<id>/probe.png`），但裸 GET 回来的是 **`text/html` 的下载页**（3132B），
   带 Cookie、带 Referer、指定 `Accept: image/*` 全都一样 ⇒ **AI 上游按裸 GET 抓，只会抓到 HTML**。
   `uguu.se` 则是干净的 `image/png`。**判据必须是对产出的 URL 做「无 Cookie / 无 Referer」的裸
   GET 看 Content-Type，不能只看上传接口返回 200。**

**三条顺带记下的**：

- **别用 `curl` 在 Windows 上测上传就下结论**：`litterbox` 在 curl 与 .NET 两种客户端下
  都回 `412 No file!`（文件没到达应用），而接口本身是活的、带 `ACAO: *`。这更像
  WAF / 中间盒，换个客户端或换网络可能就好 —— 这类失败要**如实记成「当前网络下不可用」，
  不要写成「该服务坏了」**。
- **0x0.st 已暂停上传**（原话：uploads disabled because it's been almost nothing but AI botnet spam）。
  这类免费图床寿命普遍很短，接的时候**别写死一家**。
- **大雄为什么能用 litterbox / temp.sh（已查源码，不是推测）**：它是
  **FastAPI 本地服务 + 浏览器前端**，不是纯静态站点、也不是桌面壳。`main.py` 起
  uvicorn（`app.mount("/static", StaticFiles(...))`），画布 UI 由它发给浏览器；
  前端调的是**同源**接口 `fetch('/api/cloud-video/upload')`，真正的上传在服务端用
  `httpx` 发（`upload_video_to_litterbox` / `upload_video_to_temp_sh`）。
  **同源 + 服务端发起 ⇒ CORS 这件事根本不参与。**
  ⚠ 我先前把这里猜成「桌面壳」，**方向蒙对了、形态说错了**，被用户一句
  「大雄的我看也是浏览器的画布啊」纠正 —— **别把「推断出来的机制」当结论写进记录，
  能读到源码就去读。**
- **顺带查实一条，大雄自己也踩着的坑**：`temp.sh` **只有 POST 才返回图片**
  （`Content-Type: image/png`），**GET 一律返回 HTML 下载页**（`/dl/` 变体 404、
  带完整浏览器头/Referer/`Accept: image/*` 也一样）。所以大雄把 temp.sh 的返回值
  直接当图片 URL 交给上游那段，**在上游按 GET 抓图时是坏的**；它排在 litterbox
  之后，很可能正是长期没暴露的原因。**这条对轻画是现成的教训：选图床必须连
  「上游拿到 URL 之后到底怎么取图」一起验，不能只验上传。**

### ★ 三类图片入口只有一条需要图床（2026-10-03）

用户问「什么图床？我的项目需要做吗？还有 OSS / 云电脑能关联用吗？」—— 答案取决于
**哪一条图片通路**，三条各不相同，别当成一件事：

1. **生图（图生图）** `openaiImages.ts`：浏览器 `POST /v1/images/edits` **multipart 直传字节**。
   上游拿到的是文件本身，**不需要图床**。
2. **对话 / 多模态** `openaiChat.ts`：图片编码成 `data:<mime>;base64,` 随消息发。
   多数 OpenAI 兼容站接受，**不需要图床**。
3. **视频（参考图 / 首尾帧）** `openaiVideo.ts`：上游（Agnes）官方明文要求
   「All media URLs must be publicly reachable」，而轻画素材在 IndexedDB 里、
   `data:` URL 上游也抓不到 ⇒ **这一条才需要图床**，现在被 `assertNoLocalReferenceImages`
   明确拦住报错（不是静默失败）。

**所以「要不要做图床」= 「要不要做视频的首尾帧 / 参考图」**，与生图、对话无关。
三条候选路线与取舍写在对账清单 **#106**；实现形状建议是把「assetHash → 公网 URL」
抽成注入口（与 `AssetPort`「hash → 字节」同思路），先接第三方验证，长期换 OSS / 云电脑
只换实现，`openaiVideo.ts` 与适配器不动。

### ★ 「选了一个档」必须真的落到产物上，否则只是个字段（2026-10-03）

对话窗这一轮加了三样「选择器」：加素材的两条路、模型的三档（图片 / 视频 / 对话）、
技能菜单。前两样都容易写成**只存进会话、然后就没有然后了** —— 表现是「选了下拉
自己变回去」或「选了但生成出来还是旧模型」，而测试全绿。

**三条可复用规则**：

1. **选择器要接到消费端**。图片 / 视频两档模型不能只躺在会话字段里：`recipeForGenerated`
   按计划里那个节点的 `data.mode` 选档，**连渠道一起换**（模型与渠道必须同源，否则
   会发出「A 渠道 + B 渠道的模型」这种请求），再经 `dataFor(type, node)` 落进节点。
   为此把 `dataFor` 的签名从「只管类型」改成「收那个节点」—— 只知道类型选不出该用哪一档。
2. **同一个动作有两条入口时，落位 / 建对象那段要抽出来共用**。本地上传与素材库添加
   都走 `placeAsset`；各写一遍的下场是某一条忘了避开已有节点，把素材压在别人图上
   （2026-10-01 踩过一次）。
3. **已经在别处解决过的事，去调那一份**：md → 技能的解析（`parseSkillMarkdown`）、
   素材菜单（`AssetMenu`）、模型清单（`panelModelOptions`）全部复用，一处都没另写。

**同轮那条留白已经收口**（@ 引用节点时要显示图片缩略图，参考产品图六）。难点的解法
值得记下来：chip 是 `contenteditable` 里**命令式建的 DOM**，拿不到 `useAsset` 那类 hook。
**做法是「宿主取图、编辑器就地补」**——① 把 `useAsset` 里「读 assets 表 → objectURL」
抽成非 hook 的 `loadAssetUrl`（一处实现，hook 那边也改用它）；② 编辑器给 chip 留一个
空槽、自己完全不取图；③ 宿主按草稿里的节点 id 取图并缓存，用版本号递增通知；
④ 编辑器收到后**就地**往槽里 `append` 一个 `<img>`，**绝不** `replaceChildren` ——
重建 DOM 会重置光标与输入法，用户正打字时图刚好加载完、光标一跳就是灾难。
**通用规则：拿不到 React 能力的地方（命令式 DOM / 插件 / Web Worker），把能力从宿主
传进去，而不是在那边重写一遍。**

### ★ 「让用户先确认，再告诉他不合法」是把确认当成了装饰（2026-10-02）

用户报：「我让 agent 帮我画个小猫钓鱼，流程都是对的，但是卡在了重复让我确认新建工作流上，
重复了三次，但是我的画布中没有」。链路是：模型给计划 → 弹确认卡 → **用户点了** →
这时才校验 → 整份拒绝（比如某个节点的 `order` 是字符串）→ 错误回给模型 →
它再发一版差不多的 → 又是一张确认卡。

**三条根因，各自都值得记**：

1. **校验必须在问之前**。用户点的那一下是在**为一个我们自己还没验过的请求背书**。
   现在的口径：不合法的请求**根本不弹卡**，直接把问题回给模型让它自己改
   （`agentLoop` 的 `precheck`）。
2. **形状差异不该整份拒绝**。`order` 写成字符串、`localId` 写成 `id`、连线用 `from`
   `to` —— 这些**语义唯一确定**，补得出来就该补（`normalizeAgentPlan`）。
   只有真推不出来的（不认识类型、连线指向不存在的节点）才拒绝。
3. **拦错了对象**。建节点不花钱、且是一次原子 dispatch（一次撤销全回退），
   拦它没有收益；真正该拦的是花钱那一步。用户 2026-10-02 定了口径：
   「他直接给我新建进去，但是生成与否需要让我确认，取消后也不会撤回已经新建到
   画布中的工作流」。

**另一条同源的**：工具卡的标题是**先**见 assistant 的 `toolCalls` 时按工具名定下的，
结果要等下一轮才到 —— 不改的话，一次彻底失败的计划照样顶着「工作流已创建」。
**「先按名字猜、拿到结果再修正」**这个形状在日志/步骤/通知里到处都是，
写完要回头问一句：结果回来时，我改标题了吗？

### ★ 「把这个入口去掉」= 连着到不了的链路一起撤（2026-10-02）

对话窗的「参数（比例 / 画质 / 质量）」那枚 chip 是同一天里先加上、又被用户要求撤掉的
（「agent 把参数去掉，只保留模型的选项」）。撤的时候如果**只把 UI 藏起来**，会留下一条
谁也触发不到的链路：会话字段还在、系统提示词里那段还在渲染、单测还在为它变绿 ——
**测试全绿，功能却到不了**。这正是本项目最忌讳的那种「假 ✅」的变体。

**规则：撤入口时一起撤链路**（字段 / 提示词段 / 单测 / 冒烟断言），并在对账清单里写清
「被谁取代」。想加回来就按设计文档重接一遍 —— 别指望它还在某个角落，那种「还在但没人
能用」的代码比删掉贵得多。

**同一轮的两条小账**：

- **选择器写错方向会让人以为功能坏了**：`[data-param-in="node"] button`（后代）与
  `button[data-param-in="node"]`（自身）是两个东西 —— 前者永远匹配不到，表现是
  「菜单开着但点不到选项」，花了一轮冒烟才看出来。
- **加内容到输入框里的功能，序列化只允许一份实现**：`MentionEditor`（@ 引用）与
  `TokenEditor`（变量）是两套 chip，但「DOM → 可发送文本」共用同一个 `readEditorText`。
  各写一份的话，迟早出现「界面看着有引用、发出去却没有」。

### ★ 同一条教训踩第二次：原生下拉在画布里既糙、又不可断言（2026-10-02）

M6-17 已经把**创作面板**的原生 `<select>` 换成 `ParamPicker`（chip + DOM 浮层），
理由写在那个组件类头：原生下拉的展开层由浏览器绘制，既不受画布浮层规范
（无投影 / 1px 描边 / 10px 圆角）约束，也点不动。

四个月后给对话窗加参数，**又做出了五个原生 `<select>`** —— 用户一眼看出来的不是
「挡了什么」，而是「太简陋了」。**规则：画布里的参数控件一律 `ParamPicker`，
再看到 `<select>` 就该问一句「它为什么不复用」。** 复用而不是重画，是为了让
「两处长得一样」成为结构上的事实 —— 重画一份的下场是外观漂移 + 断言锚点分裂。

**同一轮的第二条**：`ParamPicker` 类头一直写着「关闭：Esc / 点击浮层外 /
面板内点其他 chip」，但代码里**只有后两条实现了**。把它接到新调用方（对话窗）
才发现 Esc 根本关不掉。**规则：组件注释里列举的关闭 / 聚焦 / 键盘行为，
要逐条对照实现；写进注释不等于写了代码** —— 这类「文档写了、代码没有」的洞
在本项目已经反复出现，组件级注释同样算数。

**第三件，也是这一轮最值得记的一次翻车**：上面那条缺口的**第一版修法是把
Esc 监听到 `ParamPicker` 里**（document 捕获阶段）。结果 G9 冒烟当场红 ——
创作面板整块消失了。原因：Esc 是**面板级**按键策略，`CreationPanel` 用
`preventDefault()` 声明「这次 Esc 已被消费」（否则 `NodeFollowBar` 的 window
监听会顺手清空选中）；组件在 document 捕获阶段提前把它关掉，那套协议就失效了。
**规则：通用组件的「全局键盘 / 全局手势」要格外警惕 —— 它在调用方的
事件协议之前插队。缺的若是一条面板级行为，就补在面板上。**

### ★ 「同表住多类偏好」时，全表扫描必须认主键前缀（2026-10-02）

给对话窗按 liblib.tv 重排 UI（去掉选渠道、加比例/画质/质量三档）时，全量冒烟里 G95 的
★★★「确认后真的出图」是红的。**它不是 UI 改坏的** —— 把本次改动整份 `git stash` 掉、
用同一份脚本重跑，同样两条红。顺着界面抓提示条才拿到原话：
「没有渠道提供模型「Agnes 2.5 Pro」」。

**根因**：`presets` 是**一张表住三样偏好** —— 生成配方（`recipe:*`）、全局选路策略
（`routing:strategy`）、Agent 默认模型（`agent:default`）。`loadRoutingStrategy` /
`loadAgentDefault` 按**精确 id** 查，一直没事；而 `presetStore.loadAll()` 是**全表扫描**，
只用 `recipeFromRow()` 过滤字段、**没看主键前缀**。`agent:default` 那行恰好也带
`channelId` + `model` ⇒ 被读成一条生成配方 ⇒ 用户点完「设为默认模型」，该渠道的
「上次生成配方」变成对话模型 ⇒ 新建的**生成节点**带上它 ⇒ 点生成静默失败。

**可复用规则**：

- **同表多类行：写的时候加前缀，读全表的时候必须按前缀过滤。** 只靠「字段长得像不像」
  区分，迟早有一类行的字段恰好撞上（这次撞的是 `channelId` + `model`）。
- **单表里的「互不干扰」要验两个方向**：正向（各自按 id 读回自己那行）与**反向**
  （全表扫描不把别人读进来）。presetStore 原来那条断言只验了正向，所以绿了很久。
- **既有的 ★★★ 端到端断言值钱**：这次是它把「跨功能污染」照出来的。修完从红转绿、
  故障注入立刻变红，才算数。

### ★ 冒烟里 `locator.getAttribute` 不能当轮询用（2026-10-02）

定位上面那个 bug 时先被脚本坑了一次：轮询产物图写的是
`locator('[data-node-asset]').first().getAttribute('src').catch(() => '')`。
**元素还没出现时 `getAttribute` 要等满 30s 的动作超时**才 reject，于是「本该 20s 的轮询」
实际要跑 **40 分钟** —— 人只会看到「卡住了」，看不到「没出图」。

**规则**：轮询元素在不在，先 `count()`（不等待）再读属性；缺件时先记一条失败，
**不要**直接调 `selectOption` / `click` 这类会等满动作超时的动作 —— 那会把整轮冒烟
抛异常打断，前面所有断言的结果全丢。

### ★ 「多一个建节点入口」= 多一份必须同步的默认配方（2026-10-01）

给画布 Agent 补「真出图」验证时，一路走到产物那步才露出一个真 bug：**agent 建出来的生成节点
点了「生成」什么都不发生**。它不是报错，也不是按钮坏了 —— 是节点数据里 `channelId` / `model`
是空的，`toRunRequest` 遇空渠道直接返回 null ⇒ 节点不进执行计划 ⇒ `runNode` 拿到
`tasks.length === 0`，只弹一句「还没选择渠道」（用户原话那类「按钮坏了」）。

**根因是入口分叉**：`+` 菜单 / 右键 / 拖线到空白三条路都经 `createNodeWithDefaults`，
它会从渠道 store 解出**默认渠道 + 模型 + 生成参数**；agent 这条（`buildLandingCommand`）
自己写 `spec.createDefaultData()`，等于把「新建节点该带什么」实现了两遍，而其中一遍漏了。

**可复用规则**：

- **新建节点只有一份实现**（现为 `resolveDefaults` / `applyDefaults`）。新入口不许自己拼 data，
  要么调它，要么让它把结果当参数传进来（这次的 `dataFor` 就是后者的形态）。
- **「函数被调过」不是验收，数据落在节点上才是**。断言要下到 `node.data.channelId` 与
  **产物**（节点上真出现图），只断言「列表多了一个节点」会绿着放过整个坏功能。
- **异步解析 + 纯函数建命令**这条缝要显式设计：解析默认值要读库，而建命令必须纯（可单测、
  可重放）。做法是把解析结果当参数传进纯函数，而不是让纯函数去读库。
- **自检发现的 bug 也要进对账清单并带优先级**，不能只出现在对话里。

**同一轮的另一条**：agent 拖进来的素材会压在已有节点上（截图里盖住了模板的提示词节点）。
落位逻辑抽成 `findFreeRect` 后，**同一份避让规则被两个消费方共用**（整列布局 + 单节点落位）——
「同一件事写两遍」正是上一条那个 bug 的同一个形状。

### ★ 内置内容与用户内容分表：来源字段必须跟着编辑草稿走（2026-10-01）

技能库的「内置 / 用户」分表落地时，第一版把内置技能复制成用户副本并在 UI 里显示“已有副本”。

### ★ 用户说「之前那个删掉，都不对」时：先想清楚**它是建立在哪个前提上的**（2026-09-30）

融合节点的卡片我做了两版。第一版是「单张预览 + 在原图上拖框选 + 选区芯片 + 比例芯片 +
对比原图切换」，用户看完直接说：「**之前的那个东西删掉，都不对，我刚刚给你说的才对**」。

**它错不是一个控件摆错了位置，而是整块 UI 建立在一个错前提上**：我把选区当成了融合节点的
属性。用户和参考实现的前提是「**选区属于图片**」—— 在图片上「提取选区」，局部图自己带着
上下文走，融合节点只负责「一张原图 + 若干带上下文的局部图 → 合成」。前提一错，
那一整块 UI（框选、选区芯片、比例档、对比切换）就都成了多余的东西，**只能删，不能修**。

**三条可复用的**：

- **判断「该修还是该删」看前提，不看细节**。用户说「都不对」时，先去找「这块 UI 假设了
  什么」；假设错了就整块删掉，逐个控件去调只会把错前提固化下来。
- **「删干净」要写反向断言**。这一版我在冒烟里加了：`data-fusion-preview` /
  `-contexts` / `-ratio` / `-compare` 的计数**必须为 0**。删了没删干净是那种读代码
  看不出来、界面上却多一块的问题；正向断言（新东西在）永远抓不到它。
- **数据模型跟着一起收**。`FusionData` 从 `{contexts, activeContextId, assetHash,
  naturalSize, compare, ratio}` 收到只剩 `{colorMatch}` —— 留着不用的字段会让人以为
  它们还在起作用，下一次改动又会围着它们写代码。

**同一轮里另一条**：产物**从「写回融合节点自己」改成「落成右侧新节点」**（参考实现：
「结果会通过连线生成在融合节点右侧，不覆盖任何输入图片」）。这同时解决了两件事：
卡片上不必再挤一个「结果预览」，而结果节点天然带上了「完整图边界」标记、
可以直接拿去再提取下一个选区。**「东西该放在哪」往往比「怎么把它画出来」更值得先定。**

### ★ 「提取选区」：灯箱从看图工具变成框选工具时要显式切指针归属（2026-09-29）

用户口径：「图片素材，点击提取选取后，在**素材的灯箱预览界面**框选局部图，框选有比例的限制，
比例的限制在素材灯箱界面……框选后的局部图带持久性的上下文」。复用现成的素材灯箱（§6.17）
而不是另做裁剪器 —— 参考实现在这一点上写得很直白：**「插件入口应尽量复用原项目已经存在的
交互位置」（v2.0.1 / v2.1.0 两条版本记录都是这个结论）**。

**四条实现上的坑**：

1. **指针归属必须显式切换**。灯箱原本是「拖 = 平移、点空白 = 关闭」，而框选模式要「拖 = 画框」。
   两处必须同时改：① 媒体元素（`<img>` / `<video>`）上的 `onPointerDown={(e) => e.stopPropagation()}`
   是**给平移用的**，框选模式下必须让开（写成 `if (!cropping) e.stopPropagation()`），
   否则按在图上根本画不出框；② 舞台的「空白单击关闭」也要在框选模式下关掉，
   不然刚框好的框会被一次误点清掉。
2. **选区存图坐标，不存屏幕坐标**。灯箱有缩放 / 平移（复用画布那套 `zoomAt` / `panBy`），
   存屏幕坐标就得在每次 `setVp` 时重算、还容易在缩放后漂掉。存**原图像素坐标**后，
   渲染时按 `-vp.x*zoom + rect.x*zoom` 换算即可 —— 与媒体框同源，怎么缩都不会错位。
3. **视图算不出「这张局部图有没有上下文」**（需要图）。第一版忘了把这份判断注入，
   结果「线连上了、选区也在、融合按钮却是灰的」——`canRun` 还在数融合节点自己的选区。
   修法：NodeLayer 按口注入 `InputPortAsset { hash, hasContext }`（`hasContext` 由
   `resolveCropContext` 算）。**通则：任何「能不能点」的判断，只要依赖图结构，
   就必须由持有图的那一层算好注入**（架构 §4.7），别指望视图自己推。
4. **比例档抽到 domain 共用**（`layout/ratioChoices.ts`）：灯箱的「提取选区」与融合节点的
   「按模型比例提取」是同一批九档。各写一份的话，用户会在灯箱里看到 21:9、
   到融合节点却没有，自然会以为功能坏了。

**★★ 顺手记一条通用的测试手法：证明「位置对不对」必须用**有变化的图**。**
这一组原本可以拿纯色图测，但纯色图**放哪儿都一样** —— 上下文算错了照样「通过」。
换成水平渐变（`gradientPngBuffer`）之后，判据就成了「结果的渐变与原图**逐点一致**」：
上下文只要错一点（比如把整图当成了选区），渐变立刻被拉伸、断言变红。
实测三个采样点 `[40,90,40] [128,90,40] [200,90,40]` 原样对上。
**「这个断言能不能抓到我要防的那种错」比「断言过没过」重要得多。**

### ★ 共用口（kind: 'both'）：一个锚点两个方向，两个坑都在「语义反了」(2026-09-29)

用户看完融合节点后提的第一条是：「右边只需要一个端点，可以连接多个局部图」—— 这正是
参考实现的做法（`local-patch-classic.js` 那只点同时带 `in` 和 `out` 两个类，
`data-target-port="patch"`，`mousedown` 直接 `startLink(..., 'out')`）。
我在 #59 里把它拆成了「右上 patch + 右中 output」两只口，是**我自己想多了**。

实现上 `PortDecl.kind` 加了 `'both'`，规则一句话：**从它往外拖 = 出；上游落在节点那一侧 = 入**。
两个坑都踩了，而且**都不会报错**：

- **按口筛素材时漏掉 `both`**：`NodeLayer` 里「只给多输入口节点算 `inputPortAssets`」那段
  写的是 `kind === 'input'`，共用口整条被跳过 ⇒ 线明明连上了、节点里却显示
  「把一张完整原图连到左侧」（实测，靠冒烟的一条像素断言前才发现）。
  判据：**所有按 `kind` 过滤端口的地方都要问一句「`both` 算不算」**（`nearestInputPort` /
  `inputPortAssets` / `linkMenu` 的候选口 / `nodeHasPort` 四处）。
- **方向判反**：`checkConnect` 里 `if (dragPort.kind === 'output')` 决定「谁是 source」，
  `both` 落到 else 分支 ⇒ 从共用口拖到别的节点会连出**反向**的边（线连上了、语义全错）。
  现在写的是 `if (dragPort.kind !== 'input')`。**冒烟要钉住方向**：
  `data-edge-source-port` / `data-edge-target-port` / 松手菜单的 `data-link-menu-side`
  三样一起看，只断言「边数 +1」是抓不出反向的。

**顺带一条产品判断**：参考实现融合卡片上那个「颜色匹配」复选框不是装饰。用户看到我的节点
没有它，第一反应就是「色彩匹配好像没有呢」—— **能力做了但界面上看不见，等于没做**。
补上开关时顺手把「关掉之后像素真的变回原样」也写成了断言
（正中 `84,84,176` → `60,60,200`）：**开关类功能，判据必须是「拨过去之后行为真的变了」**。

### ⚠️ 一条待查的开发期告警（2026-09-29 记录，**不是**融合节点引入的）

### ★ 文档写了 ≠ 代码做了：技能库两层与映射候选（2026-09-27 第 9 轮）

**这一轮的教训是「先信文件、但必须回代码对账」。** 产品文档 §7A 早就写明技能库是
「卡片浏览 → 点击卡片编辑」两层结构，功能预设词归技能库；而代码里仍是单层

只能看代码与断言，不能看文档写了什么。**

**四条口径**（改这块前先读）：

1. **技能库两层**：第一层卡片网格（筛选 / 搜索 / 新建 / 导入），第二层编辑。

   新建走草稿，保存那一刻才落库 —— 否则用户点一下「新建」库里就多一条空技能。
2. **工作区不放「← 返回」**：导航归左侧功能栏。层级之间可以「返回浏览」，
   那是层间导航，不是页面返回。
3. **映射候选要能回落到已拉取模型**：`refreshModels` 只写 `modelCache`，
   把模型写进 `models` 是用户的勾选动作。候选若只读 `models`，用户
   「刚拉取完、还没勾选」时三个下拉全空 —— 而那正是最需要候选的时刻。
   口径落在纯函数 `routeMapOptions`，有单测钉住。
4. **Page 级 `overflow: hidden` 会连纵向一起裁**：侧栏 Logo 那次就是被它切掉呼吸动画。
   要「只裁一个方向」用 `overflow-x: clip; overflow-y: visible`。

**测试台的坑（别再把测试问题当产品缺陷）**：

- `label > input[type=checkbox]` 用 Playwright `check()` 会因冒泡触发两次

- 选择模型面板是**可滚动列表**，选项文档坐标可能远在视口外（实测 y≈1554）。
  不滚动就点，`change` 事件数为 0，看起来像「复选框是死的」。
- 自己写临时探针时若没复用冒烟的环境初始化，CSS 不加载会把模态渲染成 26px 窄条。

1. **底层是 Markdown 字符串，不是富文本**。理由是对模型更好：`##` `**` 是主流图像模型见过的语义标记，而 HTML 标签对它是噪音（占 token 不描述画面）。生成链路**完全没动**（仍是 `text` 原样发出）。
2. **没有做「透明 textarea 叠渲染层」**——试过，**不可靠**：Markdown 符号（`## ` `**`）在渲染层不占宽度、在 textarea 里占宽度，只要有一行折行两层就错位（中文长提示词必然折行），表现为「点这儿光标在那儿」。改成**左编辑 / 右预览分栏**：编辑区是带符号的真实文本（保住光标与输入法），预览隐藏符号。真正的所见即所得要完整富文本实现，是另一个量级，**未做**。
3. **节点栏与灯箱共用 `text/FormatToolbar.tsx`**，但**作用范围不同**：节点栏无光标，格式作用于**整个正文的逐行**；灯箱有真实光标，走完整的「按选区变换」。两处共用 `domain/canvas/text/markdownFormat.ts` 的同一份纯函数。

**踩过的坑（改这块前必看）**：
- **★ 双击是两态，不是单态**（用户 2026-09-21 二轮澄清）：**非编辑态双击 → 进编辑态；编辑态 + 有文字再双击 → 全选**。我曾把它简化成「永远全选」并删掉输入框，结果**双击没反应、也打不了字**（功能被改坏，用户直接报障）。这是浏览器地址栏 / Word 的通用行为，别再简化。
- **双击语义变更带动冒烟大改**：节点内那个 `textarea` 一度被删 ⇒ 多处冒烟还在找 `[data-node-type="prompt"] textarea`，全量里 G23 直接超时。已收成 `setTextViaEditor()` helper（走右键→全屏编辑），下次再改入口只改一处。
- **测试别在空文本上断言**：G64 首版「看不到 `#`」在空提示词节点上恒真（什么都没写，自然也看不到符号）。必须先 `fill('一只猫')` 再断言，故障注入（把渲染改回旧版）才会红。
- **格式按钮的「幂等」是必须的**：`applyLineFormat` 先摘旧前缀再加新前缀，否则点两次 H2 会变成 `## ## 标题`。
- **★ 格式栏是「图标 + 无文字 + 无边框」**（用户三轮反馈定稿）：① 一版是中文标签（太长，整条 809px 挤掉右侧按钮）；② 二版自带边框，渲染在跟随栏内部形成「框里有框」；③ 定稿 = 只留线性图标（`toolbar/icons.tsx` 新增 H1/H2/H3/正文/B/I/两种列表/分隔线/复制/全屏）、按钮定宽 28px、**工具栏自身 `border: none`**。跟着做时别再加回文字或边框。

### ★ 技能不是新机制，是既有链路的参数化（2026-09-24）

用户要「skill 功能」，听起来像要造一套新东西。但读代码后发现：
提示词节点上的「优化 / 翻译 / 反推」走的都是同一条链路 ——
**系统指令 + 节点正文 → 文本模型 → 结果写回**，三者唯一的差别就是那段系统指令
（写在 `PROMPT_TOOL_SYSTEM` 三个常量里）。

于是「技能」= **把那段指令从写死改成用户可管理**，执行链路一行没改。

**通则**：接到「加一个新机制」的需求时，先问**它和现有哪条链路同构**。
同构就意味着差异只在一两处参数上，参数化那两处即可 —— 比新建一套便宜一个数量级，
而且自动继承既有的取消 / 错误处理 / 撤销 / 持久化。

**配套的几个决定，理由都值得复用**：
- **复用 `presets` 表**（`skill:` 前缀）而不是新建表：两者结构同构，
  而新建表要升 Dexie schema、迁移不可逆 —— 为同构的表付这个代价不值得。
- **md 两种格式都收**：有 frontmatter 读 frontmatter（与 Codex 的 SKILL.md 同构，
  别处的 skill 能直接导入）；没有就整份当正文、文件名当名称。
  **格式要迁就用户，不是让用户迁就格式。**
- **多文件导入逐个独立成败**：其中一个坏掉不该让其余也失败。

**踩过的一个坑**：给面板加了 `useSkills()` 之后，`CreationPanel.test.ts` 里
**27 条与技能无关的断言全红** —— 因为测试没包 Provider，直接抛「未挂载」。
**给共享组件加一个新的 context 依赖时，等于给所有渲染它的测试加了前置条件**，
要一次把它们补上（本例 3 处内联 render 各补一次）。

### ★ 「分几次建计划」会让格位索引各自从 0 起算（循环落位，2026-09-24）

用户要「次数=2 时在下游生成节点右边出现两个槽位」。我第一版是**逐轮各建一个计划**：

```
第 1 轮 → buildRunPlan(...) → 该计划的 slotIndex = 0
第 2 轮 → buildRunPlan(...) → 该计划的 slotIndex = 0   ← 又是 0
```

两个承载节点因此算到**同一格位、完全重叠**。表面症状是「只有一个槽位」，
而节点数其实是对的 —— **用「数量」断言查不出来**（先写数量断言就漏了）。

**修法**：把 N 轮的任务**合并成一个计划**，让引擎按 `slotIndex / slotCount`
统一铺开。计划里的索引是「在这个计划内第几个」，跨计划没有共享上下文 ——
凡依赖「第几个」的排布（格位、序号、标题编号），都必须**在同一个计划里分配**。

**另一处**：`single` 模式下「空的下游节点」也是候选槽位，于是第一轮的产物会写进
下游节点本身、第二轮才新建。要「每轮各占一个槽位」得用 `single-alt`
（一律铺新承载节点）。**同一个 mode 参数的两种取值，落位语义相差一整类**。

**连带修正**：落位的源节点要从**循环节点**改成**下游生成节点** ——
用户的原话是「参数是靠下游生成节点控制的」，所以产物属于那次生成、
线也该从生成节点画出，而不是从循环节点。做法是把 `originNodeId`
从循环节点换成每个下游节点，落位/连线/状态就全部自然复用既有规则。

**判据教训**：这次真正有效的断言是**几何**（两个槽位的 left 都在生成节点右侧、
且 x 递增不重叠），而不是数量。数量对、位置重叠，是这类缺陷的典型形态。

### ★ 「改输入为防抖」会打断「填完就点」的既有路径（2026-09-24）

为修「批量节点里输入文字卡」，把面板提示词改成**本地草稿 + 300ms 防抖落库**。
卡顿确实没了（每键不再派发整图更新），但**冒烟 G37 从 15 秒变成 25 分钟超时**。

根因：测试里是「`fill(提示词)` → 立刻点生成」。防抖还没落库，
`toRunRequest` 读到空 prompt 就返回 null ⇒ 节点不进计划 ⇒ 生成不触发
⇒ 后续所有等待白等一遍。**不是偶发，是必然。**

修法：让测试**填完失焦**（实现在 `onBlur` 里立即落库）。
这比「把 sleep 从 200 调到 500」更好 —— 它走的是产品里真实存在的那条路径
（用户点走就是「我打完了」），而不是靠猜时长。

**通则**：凡是把「每键即时写入」改成「防抖写入」，都要问一句
**「谁会在这个窗口里读这份数据」** —— 测试、下游节点、执行计划都可能。
防抖是**延迟**，不是**不写**；延迟期间读到旧值的地方全都会受影响。
配套做法：留一个「立即 flush」的出口（失焦 / 提交），让需要确定性的调用方用它。

### ★ 画布节点里量尺寸：用 offsetHeight，别用 getBoundingClientRect（2026-09-24，缩放黑屏）

画布缩放是 `[data-world]` 上的 CSS `scale(zoom)`（见 CanvasSurface）。
于是节点内所有「量高度」的 API 分成两类：

| API | 含义 | 缩放时 |
| --- | --- | --- |
| `offsetHeight` / `offsetWidth` | **布局**尺寸 | **恒定**，不受 transform 影响 |
| `getBoundingClientRect()` | **变换后**的屏幕像素 | **随 zoom 变化** |

**凡是要写回世界坐标（`node.h` / `node.w`）的，必须用 offsetHeight。**
用错会形成反馈环：写高度 → 重排 → observer 触发 → 量到缩放值 → 写错 → 再触发……
缩放过程中高速空转 ⇒ **页面崩溃（黑屏）**。

实测（zoom=0.826）：offsetHeight=318 恒定，而 rect.height=262（318×0.826）。

**配套三条**（这次一起改的，缺一条都可能复发）：
1. 量布局尺寸（`offsetHeight`），不用屏幕矩形；
2. `node.h / node.w / emit` 走 **ref**、effect **依赖为空** —— 否则每次写回都会
   重建 effect + 重新 observe，缩放时形成重建风暴；
3. 容差至少 8px（offsetHeight 是取整值，太小会在临界点抖动）。

> 注意：getBoundingClientRect 不是不能用 —— 量**屏幕**位置（菜单定位、
> 端点坐标、拖放命中）就该用它。区别只有一个：**要写回世界坐标的，必须量布局**。

### ★ 高度自适应用「量出来」，别用「查表」——查表法必然过期（2026-09-24，第三次修）

循环节点「高度自适应」前后修了三版：

| 版本 | 做法 | 结局 |
| --- | --- | --- |
| v1 | 查表：按「通道开关状态」取高度常数 | 批次挪位置后常数过期，内容被裁 |
| v2 | 还是查表（常数改了） | 底栏改竖排后又不对，内容被裁（用户再报） |
| v3 | **ResizeObserver 量内容实际高度**写回节点 | 与布局解耦，常数不存在了 |

**教训**：凡「高度跟随内容」类需求，**第一版就该量 DOM**，不要建高度表。
查表法每次布局调整（哪怕只是挪一个按钮、改一行变两行）都会让表过期，
而过期的表现永远是你最难排查的那类——「内容被裁」或「底部留白」，
且它**不会报错**，只有用户看得到。

**实现要点**：
- 量内容层（不含节点 padding），写回节点高度 = 内容高 + padding + 边框；
- `ResizeObserver` 比定时器/RAF 稳，内容一变就触发；
- 容差取 4px，避免亚像素在临界点「放大→重排→变小→再放大」地抖动；
- 与用户手动缩放的冲突要**明确表态**：循环节点是参数卡，双向跟随（手动拉高会被压回），
  这是产品决定，写进代码注释里。

**另一条**：链上多层 `overflow` 都会裁内容。这次改了 `.card` 却还在裁，
真正裁的是**外层节点框** `.body { overflow: clip }`（全局规则，给别的节点用的）。
排查「内容被裁」时**从外往内查每一层的 overflow**，别只看你刚写的那个文件。
对循环节点放开用 `.body:has([data-loop-node])` 一条选择器，不动全局。

### ★ 「fixed 铺满视口」的页面接进壳层后会盖住侧栏（2026-09-27）

设置页的 `.page` 一直是 `position: fixed; inset: 0` —— 它当初是**独立整屏页面**，
这么写没问题。接进应用壳后它的矩形变成 **x=0 / 宽 1280**，而侧栏在 x=0..64：
页面把侧栏**整个盖住**，表现为「在设置页里点侧栏点不动」，
报错是 `page subtree intercepts pointer events`。

而壳层里每个页面都该以**工作区**为参照。
排查法：打开该页，量页面根元素的 `getBoundingClientRect().x`，
不等于工作区左沿就是它越界了。

### ★★ 把「整屏页面」改成「壳里的插槽」：先捋 `height: 100%` 那条链（应用壳，2026-09-27）

应用壳改版（左侧栏 + 右侧工作区）落地时，最花时间的不是壳本身，而是
**页面从「整屏」变成「插槽」之后暴露的一串隐藏假设**：

| 隐藏假设 | 壳层下的真相 | 表现 |
| --- | --- | --- |
| 页面用 `100vw / 100vh` 铺满 | 工作区已被侧栏减掉 64/240px | 画布横跨侧栏、左边一截被压住 |
| `body { min-height: 100% }` 够用 | **父级的 `min-height` 不算「确定高度」** | `#root { height:100% }` 解析不出来 → 壳层只有 **401px**（视口 800），下方一大块空白 |
| 有顶栏挡着，点击点要往下躲 | 顶栏已删 | 冒烟里一批「安全点击点」全部失准 |

**`height: 100%` 的链要求每一环都是确定高度**：`html → body → #root → 壳`。
任何一环写成 `min-height`，下一环的百分比就退化成按内容算。
实测：`html` 800 且 `body { min-height:100% }` ⇒ `#root` 只有 401px。

**判据要跟着「谁在遮挡」一起换**：原来断言「节点不被顶栏遮挡」、
量的是 `[data-topbar]` 的下沿；顶栏删掉后那个查询恒返回兜底值，
断言**恒真** —— 比没有断言更危险（它让人觉得有人在守）。
现在改量**侧栏右沿**。删掉一个常驻控件时，要顺手找出**所有拿它当几何基准**的地方。

**顺带挖出两个真缺陷（都不是测试问题）**：
1. **从画布进「渠道配置」再返回会丢位置**：旧画布顶栏跳设置页时带
   `state.from = 当前画布`，设置页的「← 返回」靠它才回得来。换成侧栏导航后
   没人带这个 state，用户被丢回首页、得重新找项目。修法：侧栏给 `/settings`
   带上 `state.from`（只给它 —— 别的导航项没有「返回上一处」这个按钮）。
2. **日志面板不认 `Esc`**：全项目其它浮层都认，唯独它只能点「关闭」。
   于是按了 `Esc` 面板还在、遮罩继续吃掉后续点击（冒烟里就是这么撞上的）。

### ★★ 原生滚动条：标准属性与 webkit 伪元素**只能选一套**；且 headless 测不出（2026-09-24）

用户两轮说「文本框滚动条的上下箭头还在」。我两轮都写了
`::-webkit-scrollbar-button { display: none }`，看起来无懈可击 —— 但没生效。

**根因**：同一条规则块里还留着标准的

```css

scrollbar-color: ...;
```

现代 Chromium 一看到标准属性，就切到**内置滚动条**渲染，并
**整组忽略 `::-webkit-scrollbar-*`**。于是「隐藏箭头」那条规则被连同其它
webkit 规则一起丢弃。**要自定义箭头 / 轨道 / 宽度，就不能写标准属性**；
两套混写会互相打断（Firefox 只认标准那套，取舍时以 Chromium 为主目标）。

**第二个更隐蔽的坑：headless 浏览器测不出滚动条。**

Playwright 默认 headless Chrome 使用 **overlay scrollbar**：

| | headless（overlay） | 有头（经典） |
| --- | --- | --- |
| `offsetWidth - clientWidth` | **0**（不占布局宽） | 15（默认）/ 6（我设的） |
| `::-webkit-scrollbar` | **整组忽略**（注入 40px 也无效） | 生效 |
| 上下箭头 | 没有 | **有** |

我在 headless 下量到「宽度 0、没有箭头」，据此汇报过「已修好」——
而用户屏幕上是有头 Chrome：15px、带箭头。**凡是与原生滚动条有关的量测，
必须 `chromium.launch({ headless: false })`。** 同理，一切「系统绘制」的东西
（原生控件、字体度量、DPR 相关像素）都要先确认 headless 与有头是否一致。

**怎么确认自己修对了**：不要只看自己写的声明，去 CSSOM 里把**实际规则**捞出来 ——
注意 CSS module 会把类名哈希掉（`._prompt_xxx_185::-webkit-scrollbar`），
所以按伪元素**后缀**匹配，并按「这个元素自己的类名」过滤掉页面上其它组件的同类规则
（否则会先读到别人的 `display:none`）。

**还想更进一步**：用 1×1 截图取色证明「轨道与内容同色」。
项目里没有图像解码库，但 1×1 PNG 的 IDAT 用 Node 内置 `zlib.inflateSync`
几行就能解出一条扫描线 —— 为这种一次性验证引依赖不划算。

### ★「长得像」的东西机制可以完全不同：设定 vs 动作（技能，2026-09-24）

面板上并排五个按钮：技能 · 优化 · 翻译 · 反推。**看起来是同类**（都是一排小按钮），
但用户指出它们分属两类：

- **技能 = 设定**：点一下只是「选中」，真正生效在**点生成**时；
- **优化 / 翻译 / 反推 = 动作**：点了**立刻**跑预设好的处理。

旧实现把技能做成了动作（点一下就跑 LLM）。改法的关键是**把「生效时刻」
挪到正确的位置** —— 不是改按钮，而是把技能的执行放进**执行层**：

```
点生成 → runNode → 提示词节点选了技能？ → 用技能正文当 system 跑一次 → 写回正文 → 继续跑下游
```

**为什么必须放执行层而不是按钮里**：「生成」的入口不止面板一个
（右键菜单、快捷键 R、跟随栏）。放按钮里只有面板那条路会跑技能 ——
那正是本项目反复踩的「同一功能有 N 个入口，只在其中一个生效」。

**配套的两个决定**：

- 节点存 `skillId` 而**不存技能正文**：技能在库里可改，存正文等于固化快照，
  用户改完技能老节点不动，会以为「改了没用」；
- 技能找不到时**清掉选择并提示**，不静默跳过 —— 否则用户以为技能生效了，
  实际发出去的是没处理过的正文。

**通则**：接手一排并排的按钮时，先问**「它们各自什么时候生效」**。
「点了立刻发生」和「选中、稍后生效」是两种控件，视觉上可以一样，
底层必须分开 —— 混在一起做，就会做出「点一下莫名其妙跑了一次模型」这种东西。

### ★ 面板高度：内容定高，但上限要给「锚点下方还剩多少空间」（2026-09-24）

用户要「文字多的时候不要出滚动条，自适应就好」。第一版只把
`height: 360px` 改成 `min-height: 360px` + `field-sizing: content`，
结果**面板确实长高了，但直接伸出屏幕底部** —— 参数行与生成按钮被推出可视区，
用户连点生成都点不到。

根因：面板是**绝对定位在节点下方**的，它的高度上限不能只看视口高度，
必须减掉**锚点已经在屏幕的哪个位置**。

```
可用高度 = 视口高 − 锚点 y − 底部留白
```

用 CSS 变量把这个值传给面板（`--panel-available-h`），于是三种形态都正确：

- 空间够 → 面板按内容长高（用户要的自适应）；
- 空间不够 → 面板停在上限、**自己滚**，生成按钮始终可达；
- 内容超长 → 文字框先滚（它有更小的 `max-height`）。

**另一处连带 bug**：提示词区原本是 `flex: 1 1 auto`（为「吸收 360px 面板的
剩余空间」而设）。面板改成内容定高后，它会在面板触顶时**被压扁**，
表现为**文字框第一行被裁掉**。改成不许压缩即可。
**删掉「钉死高度」这个前提时，要把它带来的一串 flex 假设一起复查。**

### ★ 删掉一个按钮 = 删掉它背后那条数据通道（提示词面板，2026-09-24）

用户说「写入节点这个功能删掉」。这个按钮**看起来**只是个按钮，
实际上是**草稿 → 正文的唯一通道**：

- 面板输入 → 写 `data.draft`
- 节点正文 = `data.text`
- 下游生成节点读的是 **`text`**
- 「写入节点」= 把 `draft` 抄进 `text`

只删按钮、不改数据流 ⇒ 面板里打的字**永远到不了下游**。
表现就是「在面板里写了提示词，生成却没反应」—— 又一种静默失效。

**所以删按钮时连带改了三处**（缺一处都不成立）：

1. `setPrompt`：面板写入从 `draft` 改成 `text`；
2. 面板回显（`buildPanelModel`）：从 `draft` 改成 `text`；
3. 面板内 LLM 工具的结果（`usePromptTools.onResult`）：也落 `text`。

`draft` 字段**留着并同步写同值** —— 老库里还有这个字段，
留着比删字段便宜，但必须同值，否则又变成「两处显示不一样」。

**通则**：接到「删掉某个按钮 / 入口」的需求时，先问
**「这个入口背后是不是唯一的写入通道」**。是的话，删它等于删掉那条语义，
必须把数据流一并改到新的落点（这里是「面板直接写正文」）。
只删 UI 不删链路，缺陷不会立刻报错 —— 它只在用户真正用的时候静默失败。

### ★ 「看起来像不像」要用计算样式和几何证明（面板工具行，2026-09-24）

用户两轮反馈都在说「像不像 / 空不空」这类**视觉一致性**问题：

1. 「左边的文字和右边的下拉的下方有空隙」→ 量出字数行与参数行间距（当时被
   `justify-content: space-between` 撑成一整条），改完 **9px**；
2. 「技能 / 优化 / 翻译 / 反推的 UI 和渠道、模型的 UI 一样」→
   不是「感觉像」，而是把两边的 `getComputedStyle` 拉出来对齐：
   **同高、同圆角、同字号字重、同样无边框透明底**。

**别用肉眼判断「一致」**：CSS module 里两处数值各写各的，
差 2px 肉眼看不出来、截图检查也容易放过。断言里直接比
`height / borderRadius / fontSize / fontWeight / borderStyle` ——
数值相等就是相等，不等就是不等。

**另一条**：`space-between` 这类「为两端对齐而生」的属性，
在只剩一个子元素时会**变成一条空隙的来源**。删掉子元素时顺手检查它的布局属性。

### ★ 一个能力「只挂在某个节点类型上」= 它在主路径上够不着（跟随素材，2026-09-24）

「跟随素材」比例档是 2026-09-17 加的，当时挂在**批量节点自己的面板**上 ——
因为那时批量的用法是「自己出图」。后来主用法变成「**批量当上游 → 下游生成节点**」，
用户是在**下游生成节点面板**改比例的，那一档就再也够不着了。

**修法不是加功能，是换判据**：从「节点是不是批量」改成
**「这次生成有没有参考图」**。有参考图就给这一档（批量自己 / 批量下游 / 普通图生图），
纯文生图不给（给了是死开关）。

**通则**：判断一个选项该不该出现时，问的是**「这个场景具备不具备它生效的前提」**，
而不是**「它当初是为哪种节点写的」**。前者随用法变化自动覆盖，
后者会在用法变了之后**静默失效** —— 功能还在、代码没坏，就是点不到。

**顺带挖出的两个真缺陷（都属于「同一条链上少传了一个字段」）**：

1. **`collectInputs` 丢 `naturalSize`**：`batch` 上游时带，`generation` 上游时不带。
   于是普通图生图选「跟随素材」永远拿不到比例，只能退化成「不指定」——
   界面上有这个选项、选了也"成功"，但比例根本没生效。
2. **取比例时 `find(i => i.naturalSize)` 会跳过第一张**：参考图 1 没有尺寸信息时，
   它悄悄跟着**参考图 2** 走了。用户看到的是「跟随素材」，实际跟随的是另一张。
   改成固定取第一张 —— 没有就**如实不指定**，不猜、不偷换。

> 这条也是「显式契约」的一个例子：`find` 那种写法**看起来**很合理
> （「找一张有尺寸的嘛」），但它没有确定的语义。凡是「跟随 X」这类规则，
> X 必须是**用户能看见、也能控制**的那一个（这里是缩略图第 1 张）。

### ★ 「下游是谁」要能区分「自己产出的」和「用户接的」（批量分发，2026-09-24）

用户要求：**批量节点的下游接生成节点时，点批量的「生成」应该驱动下游那个节点**
（用下游自己的参数），而不是批量自己出图 —— 与循环节点、提示词节点同一种「分发器」语义。

**实现本身很小**：把执行起点从批量节点换成下游生成节点即可，
集合展开 / 落位 / 连线 / 日志 / 撤销全部复用既有链路（一条线都不用新写）。

**但踩到一个必须先拆掉的陷阱**：批量节点**自己**跑过一次后，会产出承载节点
并连一条 `批量 → 承载` 的线。那些承载节点带着 `sourceData`（渠道 / 模型齐全），
于是「下游有没有可运行的生成节点」这条判据**把批量自己的产物当成了用户接的下游**
⇒ 生成按钮被劫持到那个**空提示词的承载节点**上，点下去什么都没有
（实测：点前后节点数与图数都不变，没有任何提示 —— 又一种「按钮坏了」）。

**修法**：落位建承载节点时打一个 `__carrierOf = 源节点 id` 标记，
判据里按 **id 精确相等**排除（不是「带没带这个字段」——别人产出的承载节点
对本节点而言就是普通下游）。同时把这个字段加进 `DATA_EXCLUDED`，
免得它参与指纹计算。

**为什么不能用现成的东西当判据**（两条都试过、都不行）：
- **父节点关系**：顶层分发器自己的 `parentId` 是 `null`，它产出的承载节点
  同样落成顶层 ⇒ 与用户手建的节点无法区分；
- **连线关系**：那条 `批量 → 承载` 的线正是要排除的东西，不能拿它当判据。

**通则**：当一条判据要回答「这个邻居是系统生成的，还是用户接的」时，
**让生成方自己留一个明确标记**，别去推断 —— 几何、父子、连线都可能在两种场景下重合。

**顺带的判据改进**：这类「点按钮没反应」的坑，靠读代码看不出来。本组冒烟 G71
同时钉了 ①按钮文案（`生成当前节点` ↔ `生成下游节点`）②点下去图数真的增加
③承载节点铺在**下游生成节点**右侧这三件事；其中「只有自跑承载节点时按钮文案不变」
那一条就是上面那个劫持缺陷的定点回归。

### ★ 判据必须覆盖「配好了没」，不只是「类型对不对」（循环一键运行，2026-09-23）

循环节点「一键运行」的**可点判据**最初写成 `canBuildRequest(下游)`。
它回答的是「这个节点类型**有没有可能是**运行主体」——与渠道 / 模型配没配**无关**。
结果：下游生成节点的面板还是空态，一键运行按钮却亮着；点下去什么都不发生。

**修法**：判据改成与 `emptyPlanReason` 同口径（渠道 + 模型都齐备）。
同时把 NodeLayer 里那份**抄过去的**判断删掉、改为调用同一个 `hasRunnableDownstream`
（「同一个事实只允许一个来源」）。

**通则**：凡「能不能做某事」的判断，先问清它要回答的是
**「这东西是什么」还是「这东西准备好了没」**。前者查类型，后者必须查配置。
拿类型判据当就绪判据，就会得到「按钮亮着、点了没反应」——
而这类缺陷在自动化里也容易漏（按钮确实存在、也可点）。

### ★ 循环执行的输入怎么传给下游：写自己，不改下游（2026-09-23）

循环节点要把「第 N 轮的提示词与图片」交给下游。两种做法：

1. **改写下游节点的 `prompt` 字段**，跑完再恢复；
2. **写进循环节点自己的瞬时字段**（`__roundPrompt` / `__roundAssets`），
   下游的 `collectInputs` 去读上游。

选 2。理由：做法 1 要备份 + 恢复，**异常路径漏一次就是数据损坏**（用户节点的提示词被永久改掉）；
而且语义也不对——提示词是「循环分发出来的输入」，不是「下游自己写的」。

**通则**：运行时要给下游传数据，优先传**运行期瞬时态**，不要改对方的持久化字段。
「先改再恢复」这种模式在正常路径看着没问题，异常路径就是数据事故。

### ★ flex 子项的 `min-width` 默认是 auto —— 内容会悄悄顶宽父容器（2026-09-23）

用户报「节点内部的容器没有左右居中，例如图片区域和提示词区域」。
肉眼只是「感觉没居中」，**量几何才看出真相**：面板右边缘 925，而内容区右沿 907
—— 右侧多出 **18px**。

**根因**：flex 子项的 `min-width` 默认是 `auto`（不是 0），内容会把子项撑到
比父容器还宽，父容器跟着溢出。它**不会报错、不会出滚动条**（外层还有 overflow 兜着），
只是整体偏右。

**修法**：给内容容器补 `min-width: 0`（本例三处：`.thumbRow` / `.promptList` / `.panel`），
并确认 `.panel` 有 `box-sizing: border-box`。

**验证的关键**：居中这条断言**必须先用超长内容触发溢出再量**。
空节点下内容本来就窄，缺了 `min-width` 也看不出来——实测删掉规则断言照样绿，
是假绿。塞一段 120 字无空格长文本后，故障注入（改成 `width:max-content`）立刻变红。

**通则**：`min-width: 0` / `min-height: 0` 是 flex 布局里的**必需项**，
不是可选项。凡「子项里可能放长文本 / 横向滚动内容」的容器都要写。
而这类布局缺陷的判据只能是**几何数据**（偏差几个像素），肉眼不可靠。

### ★ 复刻外部 UI：抄结构与交互，视觉换成本项目的 token（循环节点，2026-09-23）

用户要求「用我的代码复刻大雄画布的 UI」。做法：

1. **先读参考实现的源码**（`smartLoopBodyHtml` + `.loop-smart-*`），
   把它拆成「结构 / 交互 / 视觉取值」三层，而不是照着截图猜；
2. **结构、交互照抄**（分段控件、带图标开关、编号骑角、
   **数字胶囊 + 悬停快捷档位**、底栏三格）；
3. **视觉取值换成项目的**（大雄 rgba 硬编码 + `.theme-dark` 覆写 →
   轻画 CSS 变量；lucide → 内联 SVG）。

**几处照抄会踩坑、必须实测的地方**：

- 大雄的圆点用 `translate(-30%,-30%)`，在它 340 宽的节点里够用；
  轻画 240 宽、面板内距只有 8px，30% 仅移约 5px ⇒ 圆点被输入框**压住**。
  改成固定 `-9px` 才真正「骑在角上」。**百分比偏移依赖容器尺寸，换尺寸就失效。**
- 大雄的提示词面板 `flex:1 1 auto` 吸收剩余高度，在它那儿看不出问题；
  轻画节点更高 ⇒ 实测被拉到 247 高（内容只需 115），把底栏推得脱节。
  **「照抄没问题」往往只是因为参考实现的尺寸不同。**
- 浮层向上弹会盖住上方内容（大雄也这样），但改成向下弹会被节点下沿**裁掉**。
  取舍：宁可临时盖住（移开即恢复），不可被裁（点不到＝功能性失效）。

**通则**：复刻外部 UI 时，**尺寸相关的取值必须按本项目的容器重新实测**，
不能连数字一起照抄。结构可以照搬，像素要重算。

### ★ 「一处防了、另一处没防」= 整页黑屏（2026-09-23）

用户报「项目黑屏」。重启开发服务后 Vite 日志露出真实报错：

```
TypeError: Cannot read properties of undefined (reading 'length')
 > PromptNodeView.tsx:205   {data.text.length} 字
```

**根因**：同一份数据、**两处口径不一致**——上面渲染正文写了
`data.text ? … : …`（防了），下面统计字数直接读 `data.text.length`（没防）。
`text` 为 undefined 时抛异常，而 **React 渲染错误会把整棵树带下去**
⇒ 整个画布黑屏，不只是那个节点显示不出来。**用户还会丢掉未保存的操作。**

**两条通则**：
1. **视图层读节点数据一律按可选处理**。类型上「必填」只约束新写入，
   读到的数据会经历版本升级 / 老库 / 别的创建路径。崩一次的代价
   （整页白屏 + 丢操作）远大于多写一个 `?? ''`。
2. **同一份数据在同一文件里出现两次时，兜底必须同一口径**。
   「上面防了、下面没防」是最常见的漏网形态——写的时候觉得「这里刚才不是判过了吗」。
   改成先算一个兜底变量（`const text = data.text ?? ''`），只在一处处理。

**排查教训**：热更新时页面状态错乱，报错会被旧进程的日志缓存挡住。
**先重启服务再判断**——这次重启后那条报错立刻就出来了。

### ★ 引用外部设计稿：抄信息层级，不抄实现（循环节点 UI，2026-09-23）

用户拿一份 AI 生成的 HTML 原型（Tailwind + Material Symbols）来让评审。
**逐项核对后发现 4 处逻辑错误 + 3 处语义缺失**，直接搬会踩坑：

- 数字上限拍脑袋写死（起始 ≤10 / 轮次 ≤12 / 批次 ≤6），而真实边界是 9999 / 100 / 100；
- 运行进度是硬编码字符串（`运行中 2/4` 写死），真接执行时必然对不上；
- 变量只给了 `[计数]` `[总数]`，**漏了 `[进度]`**；也没提全角 `《计数》` 也认；
- **没表达「三个数字是配合工作的」**——这是最关键的缺失；
- 配色是 Tailwind 默认蓝，而本项目主色是近黑；且大量硬编码色值（本项目要明暗两套主题）；
- 用 Material Symbols 字体图标（本项目有明确教训：字形位置由字体决定，旋转/居中不可控）；
- 字号用到 9px（本项目下限 10px），且靠 `truncate` 硬截断——正是我们刚修过的「文字被裁」。

**吸收的是它的信息层级思路**（提示词收进抽屉、通道开关带数量、运行按钮写轮数），
**实现全部按本项目规范重写**。

**通则**：外部设计稿先做一遍**约束核对**再动手。视觉方向可以参考，
但颜色 / 图标 / 字号 / 数据边界这些**硬约束必须换成本项目的**，
否则等于把别人的技术债搬进来。

### ★ 高度这类数值一律实测，不靠估（循环节点，2026-09-23）

循环节点默认高度在三版里改了三次：500 → 480 → **300**，每次都因为「拍一个值」而返工。

最后一次的做法值得沿用：写个探针量 `scrollHeight` 与各块实际高度，用**数据**定值。
抽屉撑高也一样——实测需要 470，而节点框 `clientHeight` 比 `height` 少 2px（边框），
所以撑高值必须是 **474**。第一次写 470 时冒烟立刻报 2px 溢出，正是差在这 2px。

**通则**：涉及像素的取舍（高度 / 宽度 / 间距）先量再定。
「看起来差不多」和「正好放得下」差的就是那 2px，而它会被浮层边框、缩放、DPR 放大成肉眼可见的错位。

### ★ 同一功能有 N 个入口，只在其中一个生效（配方记忆·根治，2026-09-23）

配方记忆连修两版都「单测绿、真机不行」。第三版才挖到主因：

**新建生成节点有三个入口，只有左栏「＋」菜单带了默认配方。**

| 入口 | 改前 |
| --- | --- |
| 左栏「＋」菜单 | 带默认配方 |
| 画布空白**右键**菜单 | 裸 `node.create`，data 为空 |
| 拖线到空白「新建并连接」 | 同上 |

从后两个入口建的节点没有渠道/模型 ⇒ 用户改参数时配方守卫（要渠道+模型）一条都记不上
⇒ 表现就是「改了参数没带上」。

**修法**：抽 `features/canvas/createNodeWithDefaults.ts`，拆两段：
- `resolveDefaults()` **异步**（要读库拿配方）——必须在事务**外**
- `applyDefaults()` **同步**（认内存态）——可安全放进 `beginPlan`/`endPlan`

⚠️ 拆两段不是洁癖：拖线新建要求「建节点 + 连线 = **一次撤销**」，
而 `beginPlan`/`endPlan` 之间**不能有 await**（会让出事务边界，撤销断成两步）。

**通则**：新增功能时先把「有几个入口」列出来。同一个行为只在部分入口生效，
是这类缺陷的固定来源（本项目已有先例：节点导入素材、全屏编辑）。

### ★ `node.create` 的 data 是**整体替换**，不是合并（2026-09-23）

顺带踩到：给**所有**节点类型无条件注入 `{channelId, model}` 默认值，
把画板的默认数据 `{bg, strokes, texts}` 整份挤掉 ⇒ 点画板抛
`Cannot read properties of undefined (reading 'color')`，**冒烟 G21 当场变红**。

**判据**：凡是往 `node.create` 传 data，都要问一句
**「spec.createDefaultData() 里还有什么，会不会被我覆盖掉」**。
只用**白名单**（generation / batch / prompt）注入，其余类型一个字都不加。

⚠️ 还有一条**假绿**陷阱：单测里 `getSpec()` 返回 `null`（没 import `registerAllSpecs`）
⇒ `newGeneratingNodeData` 拿不到 spec 默认数据、生成节点丢掉 `mode`，而测试照过。
真机由应用启动时注册，**单测必须自己 `registerAllSpecs()`**，否则测的是空跑。

### ★ 别拿「无关的顺序」当判据（配方记忆·多渠道串味，2026-09-23）

接上一条。用户复测仍报「改了参数没带上」，但给了一条决定性线索：
**「Alt 拖动复制后的节点是带上的」**。

复制是「照着源节点拷一份」，新建是「解析链现算一个默认」——两条路完全不同。
复制能对上 ⇒ **数据是对的** ⇒ 问题只在新建那条**取值路径**上。这一句话就把范围砍掉一半。

**真因**：解析链第 2 档「按**渠道列表顺序**取第一条记过的配方」。
多渠道时，用户在渠道乙上改的参数会被排在列表前面的渠道甲那份记录盖过。
**渠道顺序与「用户最近改的是哪条」毫无关系**——拿它当判据从根上就错。

**改法**：按 `savedAt` 倒序取最近改过的那条。同时补一个隐患：`Date.now()` 只有毫秒精度，
同一毫秒内连记两次会并列 ⇒ 排序退化成渠道顺序，bug 换个形式复发。
`channelStore` 里加单调递增水位（`nextRecipeAt`），保证每次记录严格大于上次。

**通则**：
- 判据必须与**要回答的问题**同源。「哪条渠道最近被改过」只能问时间戳，
  不能问渠道列表顺序、也不能问 id 大小——那是无关的顺序。
- 「排序 + 并列」永远要一起想：只要用了时间戳排序，就问一句**同一时刻怎么办**。
- 用户给的**对照观察**（「A 能用、B 不能用」）价值极高，优先拿它做二分，别急着读代码。

### ★ 同一个事实只允许一个来源（配方记忆踩到，2026-09-23）

用户报「改了参数，再新建节点还是原本的默认」。**单测全绿，真机没通**——这本身是最大的教训：
单测里我是自己构造的参数与渠道，绕过了真实的那条链路。

**真机复现方法**（值得复用）：注入一个启用渠道 → 按用户路径操作 → 每步 dump IndexedDB 的
`presets` 表与节点 `data`。一步就看出「节点 data 变了，但 presets 一条没有」。

**两个断点都在「从哪取值」**：
- 面板用解析链算出 `shownChannelId` / `shownModel` 显示，但**节点 data 是空的**；
  记录配方时却又从节点 data 取渠道/模型 ⇒ 取到空 ⇒ 守卫把每次记录都挡掉。
- 修法：`PanelEvent` 加 `recipe?: RecipeSnapshot`，**由面板把它当前显示的整套值带出来**。
  面板是唯一知道「用户眼前这套是什么」的地方。宿主层不再自己从 store 里凑值。

**通则**：同一个事实（这里是「用户当前用的渠道/模型/参数」）只允许**一个来源**。
跨层传递时，谁手上最准就由谁带出来，而不是让下游各自再取一遍——
「两处各取一份」在本项目已经栽过多次（显示态 vs 落库态、表单态 vs 落库态、模型缓存 vs 已选模型）。

**另一条**：改动若宣称「改了 X 就生效」，验证必须覆盖**用户真实的操作顺序**，
不能只测自己构造的理想输入。G68 就是这么来的（真点、不生成、看落库）。

### ★ 「显示态」与「落库态」分叉 = 幽灵缺陷（2026-09-23）

用户报两件事，其实是同一次实测挖出来的两层：
1. **「UI 层有默认模型，但实际没有」**——新建节点后面板显示着渠道和模型，一点生成却提示「还没有选择渠道」。
2. **「没有反应点了」**——点生成按钮毫无反馈（没提示、没报错、没状态）。

**第一层的根因**：`CreationPanel` 里 `shownChannelId` / `shownModel`（**显示**，节点空时由解析链兜底）
与 `data.channelId` / `data.model`（**落库**，执行层只认这个）是两套值，而兜底当初**只写显示、不写回节点**。
于是界面看起来配好了，执行拿到的却是空 ⇒ 必然失败。

**修法**：解析链既然能算出可用配方，就**写回节点**（复用 `setChannel` / `setModel` 事件，顺序是先 channel 后 model）。
只在节点自身为空时写，不覆盖用户显式选择。

**第二层的根因**：`toRunRequest` 返回 null ⇒ 节点不进计划 ⇒ `runNode` 见 `tasks.length === 0` 直接 return。
面板上方虽挂着引导条，但**按钮仍可点**，点下去全程静默。

**修法**：①面板把「按下去必然无反应」的两种情况置灰并写明原因；
②执行层兜底 `notify` 出可读理由（抽成 `features/canvas/execution/emptyPlanReason.ts`，node 下可测）。

⚠️ **置灰的边界（G46 已踩过）**：只拦「无可用渠道」「该类别无模型」这类**必空**情形。
「有模型可选但用户没选」**不许**灰——那条路点开 chip 就能选，灰掉等于把唯一出路堵死。

**两条通则**：
- 凡「界面显示某个值、执行却用另一个值」的地方，先问**这是显示态还是落库态**；两者能分叉，就一定会分叉。
- 「点了没反应」类缺陷**无法靠读代码发现**（代码逻辑自洽、控制台不报错）。必须给出可见反馈，并用断言钉住「会给提示」而不是「什么都不发生」。

**排查教训**：想读「用户在应用内浏览器里那个项目」的数据，试过独立 chromium（读到空项目，因为数据在 IAB profile）、
整份复制 profile（Network/ 被锁）、只读复制 + classic-level（Chrome 的 IndexedDB 用 `idb_cmp1` 比较器，
与 leveldb 默认不同，打不开）。**结论：环境读不到就用①页面上的 store / DOM 锚点，②让用户报现象或控制台报错**，
不要在数据文件格式上无限深挖——那次绕路花掉的时间远超问题本身。

### ★ 不要用文本字形当图标（2026-09-22）

用户报：「左边工具栏第一个按钮 + 号旋转的不是按照图标的中心点，我不要符号，要真正的矢量图图标」。

**根因**：第一个按钮用的是文本 `＋`（全角加号），靠 `rotate(45deg)` 变 ×。
但**字形的实际位置由字体决定**——实测文字盒 36×46，而真实字形只占其中一部分，
全角 `＋` 在字体盒里偏上偏左，于是旋转绕的是一颗**偏心的点**。
`transformOrigin` 量出来是对的（18px 18px）也没用：**它绕的是文字盒的中心，不是字形的中心。**

**改法（两道保险）**：
1. 加号换成 `IconPlus`（SVG，笔画由坐标定义 ⇒ 几何中心即字形中心）；
2. **旋转挂在图标本体 `<span>` 上，不挂在按钮上**——与按钮内距无关，绕的就是图标自己。

**通则**：**任何需要精确几何行为的图标（旋转 / 对齐 / 定位），一律用 SVG，不要用文本字形。**
文本字形的宽度、位置、基线全都由字体决定，跨字体还会变。

**冒烟判据（G17，三条缺一不可）**：
- `textContent` 为空 + 有 `<svg>`（证明是矢量，不是换了个字符）；
- 图标盒中心与按钮中心偏移 ≤ 0.5px（几何上同心）；
- **悬停时图标转 45° 而按钮 transform 为 none**（证明旋转挂在图标上）。
  只断言「转了 45°」不够——偏心旋转同样能转出 45°（旧版就转得出来）。
  ⚠️ 查「有没有文本」要在**图标容器内部**找：只查按钮直接子节点会漏掉（实测假绿）。

**二轮追加：DOM 全绿 ≠ 视觉居中，要用像素质心**

换成 SVG 后用户仍反馈「锚点不在正中心」。**DOM 三层量出来全是 0**：
按钮 54×54 / 图标 39×39 / span 与 svg 中心重合 / `transform-origin` 也报在中心。
但**像素级量质心（白字形 vs 深色圆）偏 0.54px**，镜像对称性差异 4.1（完全对称应为 0）——
肉眼确实看得出来。

**根因**：图标 26px ⇒ 26 ÷ 2 = **13 的设计值在 `zoom: 1.5` 下落在半像素上**，
取整后整个字形偏一档。改 24 后 24÷2=12、×1.5=18 全是整数像素 ⇒ 偏移 0.00。

**两条通用教训**：
1. **「居中」这类几何事实，光量 DOM 不够**——盒模型全对、字形仍可能偏。
   最终判据要用**像素质心**（截 PNG 求质心差）或**镜像对称性**（翻转后比对，0 = 对称）。
2. **尺寸取偶数**，尤其在祖先挂 `zoom` 或分数倍缩放的场景：奇数尺寸 ÷ 2 会落在半像素上。
3. ⚠️ **阈值是关键**：同一缺陷在 DPR=1 下只漂 0.13px、DPR=4 下漂 0.54px。
   用 ≤1px 甚至 ≤0.25px 的阈值，0.13 照样绿（**断言形同虚设**）。
   实测正确实现是精确的 0，故阈值定 **0.05px** 才拦得住。

**★ 更大的教训：别用自己截的图当基准**

用户连续四轮说「还是偏」，我四轮都量出 0 —— 因为我**自己截图时用了 DPR=4**，
把 2px 的偏移缩成了 0.5px 的质心误差，看起来就是 0。
最后改用**用户给的原图**测量，立刻拿到实据：偏左 2px、偏下 2px
（留白 左18/右22、上22/下18；亮度加权重心复核 (−1.91, +1.91)，两个方法一致）。

**通则：判定「视觉问题」时，测量基准必须是用户看到的那个画面。**
自己复现时若改了设备像素比 / 缩放 / 视口，就可能把缺陷缩没。

**另：改 CSS 选择器前先查这个类被谁共用**

为了让加号变大，我写了 `.iconSpin > svg { width:100% }` ——
而 `.iconSpin` 是**所有按钮图标的公共类**，于是整条工具栏的图标被撑到 54px。
用户报「你怎么把我工具栏的其他图标也放大了」。
修法是加限定：`.solid .iconSpin > svg`。冒烟也补了一条防回归断言。

**★ 取消 `zoom` 时必须**逐项**换算，别只改里看的那个**

为修「加号旋转偏半像素」我取消了 `.bar` 的 `zoom: 1.5`，改成显式尺寸。**按钮换算对了**
（36 → 54），**图标却漏了**（仍是 18，应为 27）⇒ 渲染从 27 掉回 18，
用户立刻发现「其他按钮变得太小了」。

**口径**：显式值 = 原设计值 × 原 zoom。本次三处：按钮 36→54、图标 18→27、内距 6→9。
**冒烟判据用比例而不是绝对值**：图标/按钮 必须保持 **0.5**（实测 27/54）。
这样以后整体改尺寸它仍成立，而「换算漏了一半导致比例失衡」会被逮住
（把 ICON_SIZE 改回 18 ⇒ 比例 0.333，该条立刻红）。

⚠️ 同一断言的阈值也要选对：首版写「其它图标 < 按钮 × 0.5」，
而正确比例**恰好等于 0.5**，把正确实现判失败了。改 `< 0.7` 才既放过正确值、又拦住被撑满（1.0）。

**★ 还有第三处：文字（用户当天又发现「这里的文字太小了」）**

取消 zoom 的**漏换算清单**最终是四项，我分两轮才补全：
| 项 | 原值 | 挂 zoom:1.5 后 | 显式值 |
| --- | --- | --- | --- |
| 按钮 | 36 | 54 | 54 |
| 图标 | 18 | 27 | 27 |
| **文字字号** | 12 | **18** | 18 |
| **内距 / 间距 / 最小宽** | 4·8·12·160 | — | ×1.5 |

**教训：`zoom` 是整棵子树的等比缩放，不是只影响「你正在看的那个尺寸」。**
取消它时要**逐条列出该子树里所有依赖它的值**（尺寸、字号、内距、间距、min-width），
一次性换算——我分了两轮才补齐，用户也连着报了两轮。

同理，这次还把 `.menuIcon` 的图标槽（16→24）与 `.menu` 的 `min-width`（160→240）、
`padding` 一并换算，否则「图标放大而文字槽没放大」会导致左边缘对不齐。

### ★ 循环节点（§6.22，2026-09-22 落地）

用户指定参照「大雄无限画布」的 `smart-loop`（`static/js/smart-canvas.js`）。
**抄概念、不抄实现**——那边的轮次上下文是全局 `smartLoopContext`，轻画一律显式出入参。

**三条不能搞错的语义**：
1. **循环节点不产出、只分发**：`generate` 必须缺席；下游靠「连到循环节点」拿到本轮输入，
   所以 `loop` 必须进 generation / group / batch 的 `accepts.upstream`（漏了就连不上）。
2. **素材切片、提示词取模**（有意的差异）：素材取完就没了（第 4 轮不该再拿第 1 张），
   提示词可轮换复用（写 3 条跑 9 轮）。统一成一种都会错。
3. **变量两种写法都认**：`《计数》` / `[计数]`、`《总数》` / `[总数]`、`《进度》` / `[进度]`。

**实现落点**：`domain/canvas/loop/loopPlan.ts`（纯函数：归一化 / 变量替换 / 逐轮展开，20 单测）
+ `nodeSpecs/loop.ts`（接进节点体系）+ `nodes/loop/LoopNodeView.tsx`（纯参数卡）。
**没有动执行引擎**——展开成多个 task 即可，`runEngine` 零改动（理由见 §6.22）。

**UI 踩过的两个坑**：
- 节点默认高 192 时**第一条提示词被压扁**（只露半截）。修法：默认高度提到 260，

### ★ 创作面板高度：可伸展 vs 不可压缩，是两个方向（2026-09-25）

面板的「剩余空间」必须**有且只有一处吸收**，否则底部必留死白；而吸收它的那一处
又**不能被压扁**，否则内容被裁。`.promptSection` 因此踩了两次，方向正好相反：

| 版本 | 写法 | 结果 |
|---|---|---|
| 最初 | `flex: 1 1 auto; min-height: 0` | 无空白，但面板触到高度上限时这一区被压扁 ⇒ **文字框首行被裁**（30 行实测） |
| 09-24 改内容定高 | `flex: 0 0 auto` | 首行不裁了，但剩余空间没人吸收 ⇒ **底部死白 74px**（用户 2026-09-25 报） |
| 定稿 | `flex: 1 0 auto; min-height: 54px` | 两者都要：可伸展吃掉空白，不可压缩保住首行 |

**通则：改「高度由谁决定」时，要同时回答「多出来的空间归谁」与「不够时谁被牺牲」。**
只答一个，另一个就会在下一次改布局时冒出来。

配套两条：
- **`min-height` 的阈值要能反推**：面板挂 `zoom: 0.75`，故 `360 × 0.75 = 270`（屏幕像素）。
  量到「面板 270 / 内容 147」就该立刻想到是 `min-height` 在撑，而不是去查 flex。
- **空白类缺陷的断言要在「短内容」时量**：内容一长面板就被撑满、空白自然消失，
  断言恒真、什么也证明不了（本次故障注入 83px 才抓得到）。

### ★ 滚动条：写在组件里 = 迟早漏一处（2026-09-25）

**事故形态**：滚动条样式原先只写在 `CreationPanel.module.css` 的
`.prompt::-webkit-scrollbar-*`（2026-09-24 修的）。用户在**提示词节点本体**上
又看到一条又粗又带箭头的原生滚动条 —— 那个容器的 `overflow:auto` 同样存在，
只是**没人给它写样式**，于是回落系统默认（实测 **15px** 宽 + 上下箭头 + 独立底色轨道）。
同一应用里两套外观。

**根因不是「忘了写」，是「样式写在组件模块里」这个做法本身**：每多一个滚动容器，
就多一次「记得补样式」的机会，而**漏掉的表现比不做还显眼**（原生滚动条会自己冒出来）。
修法 = 搬到 `ui/base.css` 做成全局 `::-webkit-scrollbar-*`（4px），
新增滚动容器自动同款，不再需要登记。

**两条硬约束（别改，都是一次踩坑换来的）**：
1. **只写 `::-webkit-scrollbar-*`，绝不写标准的 `scrollbar-width` / `scrollbar-color`**。
   现代 Chromium 见到标准属性就切回**内置滚动条**渲染，并**整组忽略** webkit 规则
   —— 包括「隐藏箭头」那条。2026-09-24 的「写了 display:none 箭头还在」就是这么来的。
2. **轨道显式取 `--bg-surface`，不写 `transparent`**。`transparent` 在 Chromium 下
   渲染成「透出下面一层」，容器底色与父层不同时仍像多了一条槽。用户要的
   「无缝嵌入」= 显式同一个令牌。

**尺寸口径**：用户说「再缩小四分之三」→ 系统默认 15px ÷ 4 ≈ **4px**。
**一处有理由的例外**：创作面板保留 6px —— 它整体挂 `zoom: 0.75`，
全局 4px 渲染后只有 3px，抓不住。改那处前先读它自己的注释。

**测试口径（重要）**：**headless 下滚动条的真实占宽恒为 0**
（`offsetWidth - clientWidth` 量不到）。要量宽度只能读
`getComputedStyle(el, '::-webkit-scrollbar').width` —— 声明值的解析结果，
headless 也能读，被更具体规则覆盖时也会如实反映。真机尺寸另用
**有头**探针（`headless:false`）复核，本项目已验证。
- **性能剖析别信 headless 的 rAF 帧间隔**（无 vsync，恒 ~6ms）。用：每帧主线程耗时 / CDP `Profiler` / headful。卡顿多半是「每帧重算」不是「渲染慢」；A/B（`{false && <Minimap/>}`）定位浮层成本最快。
- **React 的 `onWheel` 是 passive**，`preventDefault()` 被静默忽略；要阻止页面滚动须挂原生 `{passive:false}` 监听。
- 提交前别 `git add -A`：一次性探针 `scripts/probe-*.mjs` 与搁置的漫剧调研稿不入库。
- **`git status` 干净 ≠ 目录干净**：被忽略的调试转储照样堆在项目根目录（实测 143 个 / 655KB）。
  已用 Node 清干净（2026-09-15）：**`Remove-Item`（沙箱内外的 PowerShell）与 `cmd /c del` 都被安全 shim 拦掉，
  但 Node 的 `fs.unlinkSync` / `rmSync` 可以删**——批量删文件走 Node 脚本（`%TEMP%\qinghua-cleanup.mjs` 模式）。
  白名单务必排除 `.gitignore` 与 `.dependency-cruiser.cjs`；**`.git` / `.workbuddy` 绝不能碰**。
  另：`.playwright-verify/`（235 文件 / 10MB 截图）可整个删，随时重跑再生成。
  **今后的规矩：调试输出一律 `> %TEMP%\xxx.txt`，不再落进项目根目录。**

栏与内容同色时，选中项"跳不出来"，效果同样消失。
参考图的墨绿没搬（用户要求用自己的配色），只搬了这层**明度关系**。

**用户说的 `#22242b` 是暗色主题下的 `--bg-surface`**（亮色下是 `#ffffff`）——
所以写令牌而不是硬编码那个色值：两套主题自动都对，选中项与内容在任何主题下都同色。
**别把用户给的一个具体色值直接写死**，先查它在令牌表里对应谁。

**★ 踩到的 CSS 坑（很值得记）**：想让选中项越过栏间距，我第一版写的是
`width: 100%` + `margin-right: 负值` —— **纹丝不动**。原因是块级元素同时给了
`width` 与左右 `margin` 属**过约束**，CSS 规范里 LTR 下调整的正是 `margin-right`
（它被丢弃了）。改法：直接把宽度写成 `calc(100% + 内距 + 间距 + 边框)`。
**通则：想让元素"越界"，优先改尺寸，别指望负 margin —— 过约束时它会被静默丢掉。**

**★ 还要多伸一截，否则只是"相切"而不是"连上"**（用户 2026-09-26「想个办法把这个链接在一起」）：
只把右沿**对齐**到面板左沿（差值 0）时，胶囊右端是圆角（999px），
两者只在**最中间那一个点**碰上，上下各露一道月牙缝 —— 看起来是挨着，不是连着。
正解：让选中项**继续往面板里伸** `--rail-join-overhang`，
把右侧圆角**藏进同底色面板里**（圆角看不见了 ⇒ 真连成一片）。
**伸入量必须大于胶囊半高**（实测高 36 ⇒ 半高 18，取 20）；
调大导航项 padding / 字号时要同步加大，否则圆角又会露出来。
断言因此是「overhang < 0 且 |overhang| > 半高」——**取代**了早先那条「差值=0」
（两者互斥：那条正是"相切"这个错的成因，留着它等于把错误当标准）。

### ★ 后台是「一个大容器包住左右」（2026-09-26，用户第四轮）

用户原话：「右边的具体功能框要朝左边放大包住左边的选项」。
参考图的结构至此才完全清楚：**不是一个深色侧栏 + 一个白色内容面板两个并排的框**，
而是**一个大白块**，左侧的深色选项栏是它**内部**的一块、通高到底，
右侧内容也在它内部。

改法（`SettingsPage.module.css`）：
- `.shell` 自己取 `--bg-surface` + 圆角 + `padding`，成为那个"大容器"；
- `.rail` 退化成它内部的一块深色区域：**去掉自己的描边**（否则"框里还有框"），
  并 `align-self: stretch` **通高**（原先 `flex-start` 只有三项那么高，读不出"一列"）；
- 分区自己的 `padding` 收到 16px —— 留白改由**外层 16 + 分区 16**共同给出。

**★ 一条被故障注入证伪的断言（很值得记）**：
最初我量「内容左边缘 − 大容器左边缘」来判断"内容离边缘够远"。
把 padding 改成 0 做故障注入，**它照样绿** —— 因为这段距离中间横着整条左侧选项栏（176px），
恒为 200 多 px，跟 padding 毫无关系。
改成量**右侧**（内容右边缘 → 大容器右边缘）才真正生效（0 ⇒ 16px 报红）。
**通则：量留白/间距时，先确认这段距离中间没有别的元素 —— 否则断言恒真、形同虚设。**

另：三个区是**条件渲染**的（同一时刻只有一个在 DOM 里），
任何按选择器取元素的断言都必须**先切到对应区**再量；一次性 evaluate 三个选择器
会让另外两个恒为 `undefined`（这轮踩了两次）。

接缝的数值依赖两处（`.rail` 的右内距、`.shell` 的 `--rail-gap`），
已收成一个局部变量 `--rail-gap` 并写明"改一处要连带改另一处"，避免日后调间距时裂开。

### ★★ 模型路由（M7，2026-09-26）：先量级、再动手

用户一句「参考 sub2api 和 new-api 的模型路由，做性能/价格/质量优先」，
**不能直接开工** —— 文档 §7.4.1 原定的是「逻辑名 → 上游 ID」的**单值映射**，
而「性能优先」是**多候选择路**，两者差一个量级。先调研、把范围摊开给用户定，
省掉一轮白做（用户选了 B：多候选 + 性能优先）。

**两家实现的关键差别**（都去看过源码）：

| 项目 | 模型 | 要点 |
| --- | --- | --- |
| new-api | `Ability{group,model,channel_id,enabled,priority,weight}` **物化成表** | 选路 = `priority DESC` 分档 → 档内 `weight+10` 加权随机；**retry = 降到下一档**（优先级天然是降级链）。代价：表与渠道会不一致，故它专门写了 `FixAbility()` |
| sub2api | `composite_model_route`（`public_model` + `match_type` + `upstream_model`） | `upstream_model` **空 = 恒等映射**；`priority` **值小者胜**（与 new-api 相反，抄之前先看方向） |

**本项目的选择**：候选**不物化成表**，每次按渠道**现算**
（`routeCandidatesFor`）。理由：渠道是个位数、模型几十个，现算足够快；
少一张要同步的表，就不会出现 new-api 那种「表与渠道不一致」。

**两条口径别弄反**：
  ① `attempt` 是**降级到下一档**，不是重试同一渠道；
  ② `weight+10` 的 `+10` 不能省 —— 否则权重 0 的渠道被饿死，「均衡分摊」退化。

**★ 只做有数据支撑的策略**：`priority`（手工）/ `performance`（实测 `lastTestLatency`）/
`balanced`（权重）。**价格优先 / 质量优先没做** —— 项目里没有价格表与质量评分，
做了就是假排序。已记进对账清单 #20，等数据再补（加枚举值即可）。

**★ 最有价值的一条教训**：日志原本读 `params.model`（节点意图 = 逻辑名），
于是选路生效了、日志却永远显示那个**从没被请求过**的名字 ——
G76 靠「日志里必须出现映射后的上游 ID」抓到了它。
修法是留痕加 `sentChannelId` / `sentModel`（记**实际发出**的那一份），
展示侧优先取它、缺了才回落意图。**凡「意图」与「实际」可能不同的链路，留痕都要记实际。**

**★ 选路必须也看「有没有令牌」**（同日补）：候选判据最初只有
「已启用 + 提供该模型」，会把一条**没存令牌**的渠道也选进来 ——
请求发出去必然失败，而旁边明明有一条配好的站。选路的意义正是避开这种站。
离线协议（mock）按「有令牌」处理，否则本地离线路径永远进不了选路。

**★ 多渠道才是选路的主场**：只建一条渠道时，选路恒等于「就用它」，
所有策略断言都是假的。故单独出 G77：建两条同名默认渠道 ⇒ **先改名**
（都叫「新建渠道」的话根本分辨不出选中了哪条，断言恒真）⇒ 给不同优先度
⇒ 跑一次生成 ⇒ 断言日志里的平台名是优先度更高的那条。

**⚠️ G55「最长任务 < 150ms」偶发超标（非缺陷，别去改阈值掩盖）**：
全量跑时实测到 151 / 159ms；**单独复跑三次均为 99–106ms**。
成因是全量串行跑 60+ 组、机器负载叠加，而非上传路径变慢
（G55 走上传，不经过执行选路）。判定办法：单独复跑该组，
若稳定回落到 100ms 上下即是抖动。**正确做法是查抖动，
不是把阈值从 150 调到 200** —— 那会让真正的性能回退永远不再报警。

### ★★ 选路策略必须是全局的 + 禁用渠道是硬门禁（2026-09-29 第 12 轮）

**用户口径**：模型**映射**每条渠道都要配（各站 ID 不同），但**选路规则**是
「同一个模型在多条渠道都能用时挑哪条」—— 这是**跨渠道**的事，塞进某条渠道的表单
就成了「用哪条渠道的策略」，说不清。故策略**全局唯一**，映射留在渠道。

**★ 跨渠道比较只能有一把尺子**：`resolveRouteFor` 原先读
`governingChannelId` 那条渠道的 `routeStrategy`，等于让「候选之一」定义比较规则 ——
换成另一条候选就换一把尺子。现在策略由调用方**显式传入**（执行时从
`channels.getState().routeStrategy` 读），渠道旧 `routeStrategy` 字段只为老数据兼容保留，
界面不展示、选路不读取。落库在 `presets` 保留行 `routing:strategy`（与生成配方同表、
前缀分开），非法值 / 缺字段 / 读失败统一回落 `priority`。

**★ 禁用渠道是策略之前的硬过滤**，不是靠策略「顺带」避开：候选门禁
`enabled && hasToken && upstreamModel` 先于任何排序 / 加权。禁用渠道即便优先度最高、
权重最大、延迟最低也不入选；全部禁用时返回 `null` 报错，不许硬发。写这条断言时
要专门造「禁用渠道在各维度都最优」的样本，否则断言恒真。

**界面别把全局规则塞进渠道表单**：全局卡放编辑器**顶部、渠道表单之外**，
未选中渠道也要显示（冒烟 G75 就断言这一点 + 刷新后策略仍在）。渠道卡只留
**按渠道才有意义**的优先度 / 权重 / 映射（改名「渠道权重与模型映射」）。

### ★★ M7-4 逻辑模型名：前端一个名字，各站用自己的 ID（2026-09-27）

### M7-5 固定模型显示名：前端只剩用户定的那几个名字（2026-09-27 第 7 轮）

**用户口径**：「这些只是我前端显示的名称，发送到中转的还是中转站下拉下来后
后台配置好的模型 id」。所以这**不是**新机制，而是 M7-4 那套
「逻辑名 → modelMap → 上游 ID」的**消费侧**：把下拉的数据源从
「渠道勾选的模型」换成「一份固定清单 + 渠道模型」。

**四处落地（少一处这条需求就是半成品）**：

1. `domain/project/modelPresets.ts` —— 三个常量的**逐条断言**（8 单测）。
   用户是逐个点头过的，谁加了一个他没要的名字，测试就该红。
2. `modelCatalog.panelModelOptions()` —— 固定名**排最前**，渠道勾选的跟其后。

   只看 `modelIds` 的话，用户配好映射、选路却找不到候选，表现为「填了也没用」。

**去掉平台 chip 的连坐（最容易被漏）**：生成节点不再让用户手选渠道之后，

### ★ 异步任务族与 CLI 网关族：适配器落成前的三条口径（2026-09-29）

3. **能力只声明有适配器分支的那些**。异步族没有对话适配器，就不声明 `chat`；

**轮询参数必须可注入**（`pollIntervalMs` / `sleep` / `now`）：单测要走完

断言实际打的是 `/v1/models` 这类协议自己声明的端点。

**⚠ `option.isDisabled()` 在 `<optgroup>` 里不可靠**（本轮实测）：协议下拉把

正确规则是**尺寸绝不缩、按可用宽度自然换行、整体居中、无横向溢出**。

**Lovart 字体同日落档**：其实测主西文字体是 Grilli Type 的商业字体
**GT Standard**，中文回退 **Noto Sans SC**。不要把对方站点加载的 `woff2`
直接搬进仓库；当前项目继续用系统回退栈，待用户提供授权文件后再替换字体令牌。
教训：**参考站的字号 / 比例会随页面版本变**，第一轮量到的数不是终值 ——
用户再给截图时，要重新量而不是沿用旧数，并把文档里的旧值一并改掉（否则
下一轮 AI 读到旧值会照旧值实现）。

**「展开时不跳动」的几何真相（同日）**：要 Logo 与导航图标在收起 / 展开两态
x 坐标完全不变、容器只向右扩，就必须让这两者是**左对齐**的固定锚点（收起态
`left: var(--space-2)`），而不是靠父容器 `justify-content` 居中。**另一个坑**：
`.head` 一旦有子元素改成 `position: absolute`，它会**收缩到内容宽度**而不是
占满 `100%`，此时再写 `right: 12px` 定位折叠按钮，按钮会被推到栏外 ——
必须给 `.head` 显式 `width: 100%; box-sizing: border-box`。展开态折叠按钮
靠 `margin-left: auto` 贴导航容器右边缘（实测 `toggle.right === nav.right`）。
收起态 `34×34` 与 Logo 同圆心，展开态恢复 `40×40`（与菜单项同高）。

**验证要覆盖「退化」而不只是「目标态」**：五列栅格不只量五列等高同宽，
还要量「窄工作区降成四列后不横向溢出」；居中要塞 `workspace.left/width` 和
`grid.left/width` 两侧都对，不能只看 `grid.left`。只测理想态，改窄屏必翻车。

**踩到的门禁坑**：`.playwright-verify/` 是**临时验证目录**（已在 `.gitignore`），
但之前没进 `eslint.config.js` 的 `ignores`，里面全是浏览器 `document/getComputedStyle`
的探针脚本 ⇒ `npm run check` 的 eslint 段必红。**临时验证产物要和 lint 忽略口径一致**，
已把它加进 `ignores`。另：冒烟脚本里算好 rect 只为展示、后续用 `getComputedStyle`
读样式时，那两行 `getBoundingClientRect()` 就是死变量，会触发 `no-unused-vars`，删掉即可。

**第三轮卡片/菜单精修（同日）**：参考站的卡片菜单**不是描边 pill**，而是
无描边深色圆角方块（`28×28`、圆角 `9px`）；卡片第二行只有「相对日期 · N 个节点」，
**不要工作台标签**。删掉 JSX 里的 `.wbTag` 后必须同步删 CSS 规则，否则会留下
不会被发现的死样式。断言也不能只看「按钮存在」：要量尺寸、`border-width: 0px`、
`border-radius` 和**非透明背景**，否则旧的描边圆胶囊照样能通过。

### ★ 裁切要逐层查，改一层不够（2026-09-28 Logo 再次被裁）

`#36` 修的是侧栏 `.rail` 的 `overflow: hidden`（改成 `overflow-x: clip; overflow-y: visible`），
当时截图确认没切。这次用户又报「动态 Logo 被容器切割」——根因在**外层 `.shell`**：
它仍是 `overflow: hidden`，猫画图标呼吸动画缩放到 1.04 越过侧栏顶部时，被**壳层**纵向切平。
**教训**：DOM 里每一层带 `overflow` 的祖先都会裁，修了内层不等于外层放行。
定位这类问题要在浏览器里**从元素往上逐层看 `overflow` / `clip`**，不能只盯直接父级。
改法与 `.rail` 一致：`overflow-x: clip; overflow-y: visible`——横向仍裁、纵向放行，
页面内部滚动继续由各工作区页面自己承担。

### ★ 画布去网格：连只为它服务的常量一起删（2026-09-28）

用户拍板「画布不要网格」。删除 `GridLayer` 组件 + `<GridLayer>` 挂载之外，
**必须顺手删掉只给它用的 `GRID_SIZE` / `ZOOM_HIDE_GRID_BELOW` / `ZOOM_FADE_GRID_ABOVE`**，
否则留下的常量会成为「看起来还在用」的误导线索。
**注意别误删 `--grid-line` 令牌**：项目卡片无封面时的 24px 占位背景仍用它，
删了会让占位样式静默回退成无背景。判断依据是「还有没有别的消费方」，而不是名字里带「网格」。
验证不能只断言「`GridLayer` 元素不存在」——网格也可能是纯 CSS 背景画的，
要同时量画布底的 `background-image` 不含 `gradient`。

### ★ 映射区只列固定行，上游 ID 只做候选（2026-09-28）

设置页模型映射区**只由 `PRESET_MODELS` 出行**——固定 15 行（生图 6 / 对话 4 / 视频 5）。
上游拉取 / 保存回来的模型 ID **只作为该行的下拉候选**（`routeMapOptions(...)`），
不许自成一行：一旦让「已保存的上游裸 ID」也出行，用户每拉一次模型就多长一行，
映射区会无限膨胀，且和「前端只暴露固定显示名」这条口径直接冲突。
判断信号：**拉取动作是「候选变多」，还是「行数变多」？** 后者一定是错的。

同类几何坑：给「两栏卡片里的表单」量居中时，**参照系必须是表单真正所在的右栏**，
不是整张卡片（卡片含 264px 左栏，拿整卡中心比会稳定偏右约半个侧栏，
把正确的居中误判成失败）。为此给编辑区挂了 `data-settings-editor`。

### ★ 铺满工作区 ≠ 不能整组居中：拆成「舞台 + 内容块」两层（2026-09-28）

设置页先有「卡片必须铺满工作区」的几何断言（G45 / G74：卡片宽 ≥ 工作区宽 − 40），
后又有「左列表 + 右编辑整组要居中」的诉求，看着像互相打架，其实是**量错了对象**：
铺满约束的是**外层舞台**，居中约束的是**舞台里的内容块**。
做法：`.layout` 保留满宽 + `display:flex; justify-content:center`（仍满足宽度口径），
新增 `.workarea`（`max-width` 定宽、`width:100%`）承载真正的两栏栅格；外层照旧铺满，
内层随工作区收窄并居中。冒烟里两条断言并存：一条量舞台宽度，一条量内容块中心。

**教训**：同一容器被两条相反口径「拉扯」时，先问是不是该拆成两层，而不是二选一。
另外上一轮只把右侧表单在编辑列里居中，用户看到的却是「整块偏左」——
**局部居中不等于整体居中**，汇报「已居中」前要按用户实际看的那个组合体量一次。

### ★ 隐藏原生 checkbox 别用 `clip`：自动化 `check()` 会静默失败（2026-09-28 设置页开关）

设置页「已启用」从裸 checkbox 改成轨道式开关时，第一版沿用网上常见的隐藏写法：
`position:absolute` + `clip: rect(0 0 0 0)` + `width/height: 1px`。
真人点击没问题，但 Playwright 的 `isVisible()` 判它不可见，`check()` **不报错、也不生效**——
渠道没被真正启用，画布侧于是误报「没有选择渠道」。这种「静默失败」比抛异常更难查：
测试全绿只是因为它根本没操作到那个控件。

**正确做法**：原生 checkbox **保留在与可见轨道等大的命中层上**，只把 `opacity` 设为 0。
`appearance: none` 抹掉 UA 外观，`width/height` 与轨道一致，`top/left` 对齐轨道。
这样命中区、键盘焦点、无障碍语义（`checked` / `aria`）都还在，自动化与真人走同一条路径。

**判断信号**：一个「隐藏的原生控件」如果测试里 `check()` 或 `click()` 之后状态没变，
先量它的可见性，别怀疑业务逻辑。凡是要被自动化操作的控件，都别裁成 1px。

同类提醒：列表级操作（新增 / 删除渠道）曾靠父容器 `flex: 1` 被推到左栏最底部，
渠道少时与条目隔着大片空白。改法是把它们并入列表、作为**最后一个子项**紧跟末条，
而不是在底部再包一层固定区——「视线不用跨越空白」才是这类排版的判据。

### ★ 居中舞台模式：外层铺满，内层内容块居中（2026-09-28 技能库）

「内容要在工作区居中」和「容器必须铺满工作区」两条口径同时存在时，不要二选一，
拆成两层即可：外层舞台 `width:100%` 仍然铺满，内层内容块 `margin-inline:auto`
加 `max-width` 收窄居中。技能库三层（浏览 1120px / 编辑 900px / 预设词 900px）
都用这个模式；设置页的两栏组合体是同一个模式的先例。

配套排版规则：同一行卡片要等高就把 `grid-auto-rows: min-content` 去掉，
再用 `margin-top:auto` 把元信息压到底；卡片里的名称与说明必须有 `min-width:0`，
否则长文本撑破卡片。字号不要硬编码，统一走 `--fs-*` 令牌。

### ★ 多层工作区改版：验证与几何断言必须覆盖每一层（2026-09-28 技能库）

技能库有浏览 / 编辑 / 功能预设词三层。只量第一层的居中会把另外两层的贴左漏掉；
三层各自挂 `data-*-stage` 锚点，再用同一个 `centerOffset(sel)` 量「舞台中心
与 `[data-app-workspace]` 中心的偏差 ≤2px」，才能钉住「都要居中」。
长文本溢出也按层取样：名称 24 字 + 说明 55 字，卡片与内部 `span` 都查
`scrollWidth <= clientWidth + 1`。

### ★ Playwright 启动必须指定 `channel: 'chrome'`（2026-09-28 技能库）

本机默认 headless shell 未安装，`chromium.launch()` 直接起不来。临时探针与
截图脚本一律用 `chromium.launch({ channel: 'chrome' })`；像素 / 几何结论仍以
`scripts/smoke.mjs` 的有头链路为准，临时脚本不要复用页面初始化。

### ★ 圆钮图标不要用 `＋` / `×` 字形（2026-09-28 循环节点）

文本字形的视觉边界受字体度量影响，即使外层 `flex` 居中，在圆钮里看仍会偏。
圆钮内统一用关于 viewBox 中心对称的 SVG，容器用 `grid + place-items:center`，
并给图标自身固定宽高。深色主题的选中态用 `--control-inverse-bg` /
`--control-inverse-text`，不要用 `--accent*`，后者在深色主题会翻成浅底深字。

### ★ 画布世界层不要写 `will-change: transform`（2026-09-28 循环节点）

它会预提升合成层，和节点内部 `container-type` 在非整数缩放下共同作用，
表现为节点模糊或只有一部分清晰。保持 `will-change:auto`，由浏览器在缩放时正常栅格化；
冒烟 G67 以世界层 `will-change=auto` 作为回归钉子。

### ★ 协议是「声明」不是「开关」：一站一协议（2026-09-28）

用户要的「一个站一个协议」不是把三个协议合并成下拉里的一个选项，而是把协议
**从互斥的适配器开关升格为一份声明**：`ProtocolDefinition` 同时带 `family`
（哪个适配器实现）、`capabilities`（这个站有哪些能力）、`versionPath`（版本段）、
`defaultBaseUrl`（站点默认地址）。渠道因此只建一条，同一站的对话 / 生图模型
靠 `ModelCapability.category` 分流到不同节点，不再需要为同一个中转建两条渠道。

**三条硬边界，决定了哪些条目是 `ready`、哪些只能是 `pending`**：

- **没有官方依据的端点不写死**。宁可 `pending`、界面不可选，也不填一个猜出来的
  路径——「文档里写了 ≠ 实现里有」，写死错端点只会让用户在「验证失败」里绕圈。
- **领域层没有的能力不假装支持**。`ModelCapability.category` 当时只有
  `chat | image | video`，没有音频与 3D，协议 `capabilities` 就只到这三项；
  自建协议更只开放对话 / 生图，视频被过滤掉。
- **纯 Web 应用跑不了本机 CLI**。即梦 / GPT / Gemini CLI 必须先有专用网关，
  没有网关时只能是 pending，不能给个空壳让用户以为配好了。

**「第一个通过的协议」是假动作，探测必须只问一个问题**：改造前
`openai-images` 与 `openai-chat` 的验证都只打 `GET /v1/models`，同一个中继
必然被两条同时命中，协议落在哪条全看候选表顺序（M6-16）。现在探测只留一条
通用模板 `openai-compatible`，它只回答「这个地址是不是 OpenAI 兼容 HTTP」，
不再冒充「能力归属」；命中后按 host 反查站点身份（`stationProtocolForUrl`），
让用户填了玉玉地址就显示玉玉而不是「OpenAI 兼容」。

**地址归一是「版本段声明 + 补一次」**，不是无条件拼 `/v1` 也不是无条件剥 `/vN`：
前者把「地址已含 `/v1`」变成 `/v1/v1/models`（一律 404），后者把火山 Ark 的
`/api/v3` 剥成 `/api`。正确口径是 `resolveProtocolBaseUrl(raw, versionPath)`：
**已以本协议版本段结尾就原样用，否则先剥掉结尾的版本段再补一次**。

**用户能自建，但只开放结构简单的一族**：用户在界面上可以新增 OpenAI 兼容协议
（名称 / 短标签 / 标识 / 能力 / 默认地址 / 版本段 / 文档地址），校验后落独立
的 `customProtocols` 表（不污染 `presets` 的配方命名空间），可删除；CLI 包装、
异步轮询、站点私有字段这些必须内置适配器承担，用户拼不出——允许他拼等于让他
配一条跑不通的渠道。校验规则只写在 `validateCustomProtocol` 一处，界面 / 导入 /
单测三个入口共用；被渠道引用时阻止删除并说明原因。

**老 id 必须原样保留**：`openai-images` / `openai-chat` 的 id 改了，等于让所有
已配置渠道升级后变成「未知协议」。所以它们留在目录里、标 `legacy`、只解释不改名。

**新增 IndexedDB 表要升 schema 版本**：`customProtocols` 走
`this.version(4).stores({ customProtocols: 'id' })`，Dexie 只声明新增表，
其余表延续上一版。

### ★ 手动收藏素材库（2026-09-29，#61，取代 #55）

用户明确否掉了“把所有画布素材汇总成历史库”的第一版：**只有从生成节点主动保存的素材才进入 `/assets`**。因此必须把内容仓库与收藏列表分成两张表、两种语义：

- `assets`：内容寻址字节仓库。生成、上传、画布引用都只碰它。
- `assetLibrary`：一 hash 一行的收藏关系 + 保存当时冻结的提示词 / 模型 / 比例 / 画质 / 渠道 / 像素 / `savedAt`。`/assets` 只列这张表。

**取消收藏只删 `assetLibrary` 行**，绝不删 `assets` 字节或改画布节点。画布可能仍引用同一 hash，删字节会把用户看不见的地方弄坏。

**快照冻结而不是每次回查节点**：保存时用目标 hash 找最新成功 `runRecord`，渠道 / 模型优先取 `sentChannelId` / `sentModel`，参数优先取记录快照，像素按“运行记录成对尺寸 → 节点 naturalSize → assets 行成对尺寸”回落；缺素材行时返回 null，不伪造一条没有字节的收藏。保存后节点再改，收藏不被回写。

**保存入口只放在右键菜单**（用户定稿）：节点右上角素材菜单仍只做清空 / 替换，生成节点右键持有素材时列出“保存到素材库”。入口调用 `features/canvas/saveAssetToLibrary.ts`；不要再把保存塞回节点右上角。

**瀑布流仍用 CSS `columns: 240px`，但展示语义已改**：卡片不再有项目 / 时间 / 体积文字，媒体用 `object-fit: contain` 完整显示；比例不再夹取。单击只选中，双击才开灯箱——浏览器双击前必先发单击，所以 onClick 只能做选中，onDoubleClick 才开。灯箱不是“卡片套卡片”：左侧媒体舞台无内框，右侧固定信息栏；配色是色块 + 色值墙，提示词是独立阅读块，技术信息是紧凑网格。右侧顺序固定：配色 / 原提示词 / 像素 / 比例 / 画质 / 模型 / 渠道。

**验证覆盖“看起来像但语义错”**：G90 故意在 `assets` 多放一张未收藏图，页面若仍扫描 `assets` 就会多卡片；取消收藏后用 IndexedDB 直接断言 `assetLibrary` 少一行、`assets` 仍保留 hash；空库提示必须精确等于“从生成节点保存素材后才会出现在这里。”。

### ★ 设置页下拉别用原生控件、字号视觉要复刻画布参数 chip（2026-09-29 第 13 轮）

用户对设置页「选路策略 / 模型映射」的判断是「跟没设计过一样」，要的是**生图节点
参数 `ParamPicker` 那一套**：chip 触发器 + 浮层菜单，而不是系统 `<select>` /
`<datalist>`。三件事记牢：

1. **不复用 `ParamPicker` 本体**。它 `import` 了画布布局常量
   `RATIO_FOLLOW_SOURCE`，设置页反向依赖画布会把两个界面的生命周期绑死
   （画布改比例档位会牵动后台设置页）。正确做法是按**同一套视觉口径**在设置页
   另写一份 `SettingsPicker`（chip 46px、浮层 `--bg-surface` + 1px `--stroke` +
   `--radius-control`、无投影、菜单行 44px、选中行 `--bg-hover` + 行尾勾、点浮层
   外 / Esc 关闭）。
2. **`<datalist>` 必须换掉**。它的候选列表由浏览器绘制，既不受浮层规范约束，
   Playwright 也读不到——冒烟无法断言。模型映射改成「可手填输入框 + 右侧下拉
   开关」的 `ModelMapCombo`，菜单项挂 `data-route-map-option` + `data-value`
   才可被自动化和像素断言。
3. **两种控件的刻意差异要留在注释里**：chip 保留描边（与同页 `.input` 同一副
   面孔；表单里一个完全透明的可点区会被当成静态文字）、浮层左对齐（表单是一列
   左对齐字段，画布参数是水平居中）。

2. **同一条配置在两条链路上表现不一致时，先怀疑「有一边少查了一样东西」**，

### ★ 真机复现技巧：把用户的浏览器配置整份复制到临时配置（2026-09-30）

用户报「生成不了」而本机又没有他的数据时，最快的路是**复制他的浏览器 profile**：
Codex 内浏览器（IAB）的分区在

（令牌密文在**同级的 `Local Storage\leveldb`** —— 凭据走 `localStorage`，不在 IndexedDB

user-data-dir 的 `Default/` 下，用 Playwright 的 `launchPersistentContext` 打开
`http://127.0.0.1:1420` 就是**用户本人的数据**。再把 `page.route('**://<站点>/**')`
一拦（`route.abort()`），就能看到真实的请求体、又不会花用户的钱。
这招也让「修前 / 修后」的对照变成硬证据（修前 0 请求 + 控制台抛错，修后请求真的发出去）。

**2026-10-01 补两条（这次读渠道数据踩到的）**：

1. **必须挑对库**：同一分区里有多个 IndexedDB —— `canvasflow`（**旧库，残留**）与 `qinghua`

   于是看到几年前的渠道、还以为用户数据就这样。正确做法：先 `indexedDB.databases()` 全列出来，
   逐个读，并用**页面上真实渲染出的渠道条目**（DOM 锚点）交叉验证读到的是不是同一份。
2. **登录态在 localStorage**：只拷 `IndexedDB` 仍能读到业务数据；但要让页面自己跑起来
   （走 store 而不是裸读表），`Local Storage` 也得一起拷。

现成的探针：`scripts/probe-user-channels.mjs`（`.gitignore` 已排除 `scripts/probe-*.mjs`）。
读用户数据一律**只读副本**，并把外部网络全 abort —— 既不会写坏原件，也不会花用户的钱。

### ★ 参考图定的是**结果形态**，别用「更保守的实现」去顶替（2026-09-30 第 2 轮）

用户给大雄融合卡片的截图，只说了一句「他就是铺满的，而且左右分区的」。上一版我为了

更不容易出错**，但和参考图长得不一样，就是错。改法：原图回 `cover` 铺满；右列高度锁死在
左格（行高由 `.paneOriginal` 的 `aspect-ratio: 1` 决定），每张 `flex: 1 1 0` 等分，贴到
可读地板（44px）后由列内滚动接手（参考图右列本来就有细滚动条）。教训：**居中不裁（contain）
与铺满（cover）是两种设计意图，用户给了参考图就按参考图选，别按「哪个更安全」选**。

同一轮的通用交互常识：**一次性画框工具里，「按在已有选区上」必须是操作它**（搬框），不是
再画一个 —— 首版把「按在图上」一律当画新框，用户想微调位置只能重画，报的就是「在选取内
拖动每次都会新建一个选取」。落地手法：在选区内铺一层 `[data-lightbox-crop-move]`（`inset:0`
`cursor:move`）接管指针，8 个手柄放在它上面（压角时手柄优先），于是「内=搬、外=画」由层级
天然表达，不靠坐标判断。

### ★ 「对比原图」这类**配对**要写进产物数据，别靠连线反推（2026-09-30 第 3 轮）

用户：「融合节点出的结果图双击出现灯箱后要有对比原图的功能」。配对存
`GenerationData.compareWith = 原图的 assetHash`，在**产出那一刻**写死：连线是活状态
（上游换图 / 删线都会变），而「这张结果是从哪张原图融出来的」是**既成事实**。
存 hash 不存节点 id —— 素材内容寻址，复制粘贴 / 换节点都不会指错；读不到配对时
对比入口不出现，不给点不通的开关。

落地还有两点值得复用：① **灯箱侧不扩事件参数**：灯箱自己能读 `store.getSnapshot()`，
按「assetHash 相同 + 带 compareWith」把配对找回来，省掉一路从节点视图透传到灯箱的 plumbing；
② 对比档的整块几何（box / 选区 / 分割线）一律按**主图（结果）**的尺寸算 —— 切到「原图」档时

### ★ 卡片分两种：**参数卡**高度跟内容、**看图卡**内容跟节点（2026-09-30 第 4 轮）

用户报「融合节点右下角放大时会跳动」。根因是**两条规则互相顶**：预览列表用
`aspect-ratio: 1` 撑出内容高，而节点又被 `ResizeObserver` 按内容高写回尺寸 ——
拖拽中高度先被拖大、紧接着被自适应写回，松手再补一跳（实测 306 → 332）。

判据很简单：**这张卡是「读参数」还是「看图」**。循环节点是参数卡（内容行数决定高度），
所以它量高度写回；融合卡是看图卡（预览区该吃掉剩余空间），所以删掉高度写回、让
`.content` 撑满 + `.panes` 用 `flex: 1 1 auto` 吃剩余高。照搬另一种卡的自适应，
就是这类「拖一下就跳」的固定来源。顺带一条：**内外边距要同档** —— `padding: 8px 12px`
这种通用写法放到「大色块贴边」的卡上，左右比上下宽 4px 一眼就看出来不齐。

### ★ 「松手之后尺寸不再变化」是缩放的唯一不变式（2026-09-30 第 5 轮）

用户：「好像节点的缩放都会出现一些问题」。写了个一次性脚本把**八种节点类型**逐个拖
右下角量了一遍（记录拖动轨迹 / 松手前后 / 跟指针量），结论是**只有循环节点真坏**，
其余各型的差异都是设计内的锁比（生成节点按产物比例、分组 / 批量 5:4、对比按当前比例）。

循环节点坏在两处，都值得记：

1. **同一个常量兼任两个语义**：`NODE_MINIMUMS.loop.h = 380` 既是「新建时的尺寸」
   又是「缩放下限」，而内容自适应早把节点收到 320 ⇒ 用户一碰右下角就被夹回 380
   （主观感受就是「一跳」）。默认尺寸与下限是两件事，别用一个常量表达，
   尤其当另一条规则会持续改写它的时候。
2. **写回只挂在 `ResizeObserver` 上**：它**只在内容尺寸变化时**触发 ⇒ 某次量到拖拽
   中间态写高之后，内容不再变、RO 不再触发，那个过高值**永远留在那儿**（332 → 380）。
   修法：写回改成 `useLayoutEffect` 每帧自检（幂等自愈、容差 4px），RO 只保留
   「内容自己变了」这条路径；`NodeFrame` 另存 `nodeRef` 取**最新**高度，
   免得用按下那一刻的旧值把内容写回顶掉（否则每帧来回一次，看着就是抽搐）。

### ★ 图标一律内联 SVG，禁用文本字形（2026-09-30 第 6 轮）

### ⛔ dev server 会发**陈旧的 CSS 模块**：改完样式量不到变化（2026-09-30）

改完 `NodeFollowBar.module.css`（图标位 26px → 16px）后，用 Playwright 量 DOM 仍是旧值：

### ★ 两级间距要**分开定档**：内部贴紧、外部留一格（2026-09-30 第 7 轮）

跟随栏的间距被用户打回两次，方向还相反：先说「图标和名称靠的太远」（图标↔文字 9px），

### ★ 接第三方 API：先拿无效参数探端点，再拿最小参数跑真链路（2026-10-01）

### ★★ HTTP 头要用「不区分大小写」的方式合并，否则浏览器会拼成重复值（2026-10-01）

接 Agnes 视频时，**同一段适配器代码在 PowerShell 里跑得通、在浏览器里一定 400**。
服务端原话是「该接口仅支持 Content-Type: application/json，请发送 JSON 请求体」——
看着像「没带 JSON 头」，实际是**带了两次**。

根因在 `fetchNetwork.requestInit`：默认项写成 `content-type`，渠道层普遍写
`Content-Type`，旧实现是 `{ ...base, ...req.headers }`。JS 对象**区分大小写**，
两个键同时存在；交给 `fetch` 后浏览器把同名头**按逗号拼接**，真发出去的是
`content-type: application/json, application/json`。服务端判定不是合法 JSON → 400。

两条教训：

1. **HTTP 头名不区分大小写，合并时必须先 `toLowerCase()`**。别用对象展开「覆盖」头，
   那只能覆盖键名完全相同的那一种写法。
2. **mock 渠道不走网络层，这类 bug 它照不到**。所以「冒烟全绿」不能证明真实渠道的
   请求形态对——真渠道的第一次调用必须自己真跑一遍看响应。

诊断手法值得复用：拿同一个端点，用 shell 试 `Content-Type: application/json` 与
`application/json, application/json` 两种值。后者如果复现出服务端那句报错，
就锁定是重复头，而不是「头没发出去」。

### ★★ Range 是「活的」：删一个字符，它自己的偏移也会跟着挪（2026-10-02）

用户报「有些时候按艾特的时候要选择两下才能输入」。真因不在菜单，在**插入引用**那一步：

```ts

;(node as Text).deleteData(range.startOffset - 1, 1)
range.setStart(node, range.startOffset - 1)   // ← 这里的 startOffset 已经变小了
```

`Range` 是**活对象**：`deleteData` 删掉一个字符时，覆盖到那段文字的所有 Range 偏移会
**自己往前挪一格**（这是规范行为，不是浏览器 bug）。于是第二行的 `startOffset - 1`
算出 `-1` → 浏览器抛 `IndexSizeError` → 后面的 `insertNode(chip)` 根本没跑，
而 `@` 已经被删掉了。用户看到的就是「点一次没反应，得点第二下」。

三条教训：

1. **改完 DOM 之后要重新读 Range 的位置**，别拿改之前算好的偏移直接用；
   拿不准就 `Math.max(0, Math.min(offset, node.length))` 夹一道。
2. **测试要覆盖「真用户那条路」**：这个 bug 活了很久，因为所有 @ 用例走的都是
   **点工具条按钮**——那条路进的是 `else` 分支（直接 append），压根碰不到这段代码。
   补的一条是「在输入框里打 `@` → 点**一次**选项 → chip 必须在」＋「不再抛 IndexSizeError」。
3. **`page.on('pageerror')` 是这类「静默半途失败」的唯一线索**：界面看不出报错，
  只有 pageerror 里有 `IndexSizeError`。冒烟里那条断言就是盯它。

### ★★ `preventDefault()` 会取消「滚到最近的滚动容器」（2026-10-03）

用户报：「面板如果有多余的地方的话用滚轮无法下拉，而是缩放画布了」。

画布为了接管滚轮缩放，在根节点上挂了 `wheel` 监听并**无条件** `preventDefault()`。
而 `preventDefault()` 取消的**不只是**页面滚动 —— 它同时取消了「滚到最近的滚动容器」
这个默认动作。于是参数浮层里那列放不下的选项（`overflow-y: auto`）**一个都滚不动**，
画布反倒缩放了。用户眼里就是「这个面板坏了一半」。

正确的判据是**按祖先链让路**：从 `event.target` 往上走，链上只要有一处
**真能滚**（`overflow-y: auto/scroll` 且 `scrollHeight > clientHeight`）就把滚轮留给它。
不能只看「是不是文本输入框」—— 那只覆盖了最明显的一类。

三条配套细节，缺一条都会翻车：

1. **装得下的 `auto` 容器不让**。只看 `overflow-y: auto` 就放行的话，一个刚好装下内容的
   `auto` 容器会让画布缩放**莫名其妙地失灵**。必须比 `scrollHeight / clientHeight`。
2. **菜单要能声明「我吃滚轮」**（`data-wheel-owner`）。选项刚好装得下时它并不「能滚」，
   但滚轮也不该穿到底下的画布 —— 那是用户没在看的另一层。
3. **滚动容器加 `overscroll-behavior: contain`**：滚到头之后别再把事件串给外面。

判据抽成纯函数（`features/shared/wheelTarget.ts`）后可以直接单测 ——
这类「边界该让给谁」的逻辑写在事件回调里，就只能靠真机一次次试出来。

### ★★ `zoom` 元素里的 px 与外面不是一套（2026-10-03）

创作面板挂着 `zoom: 0.75`，而它的**可用高度**由 JS 按视口算出来（屏幕像素）。
两边直接相乘的后果有两个，都是用户先看到、代码后知道：

- `min-height: 360px` 是**无条件**的，可用高度比它小时面板照样长到 360px ⇒
  **底部那一行（参数 + 生成按钮）被顶出视口**，用户既看不到也点不到；
- 同一个变量当成 `max-height` 用，等于预算打了七五折（给 256px 只渲染 192px）。

修法：JS 侧把值**换算成面板内部单位**再挂上去，并且让 CSS 的 `zoom` 也从 JS 取
（`--panel-zoom`，单一来源）；CSS 侧 `min-height: min(360px, var(--panel-available-h))`
—— 下限也要跟着可用空间走，不能写死。

**通则**：任何「跨 `zoom` / `transform: scale` 边界传尺寸」的地方都要问一句
「这个数是哪套单位」。

### ★★ 写死的 `max-height` 会把内容「在边框内切掉」（2026-10-03）

用户第二天的追加反馈：「参数面板里面的内容能完全显示吗？我不想要内容超出边界」。

参数浮层的 `max-height` 当时写死 420px，而 13 档比例网格本身就有 5 行 ——
于是最后几行**被边框裁掉**。这比「弹窗太长」糟糕得多：长的弹窗用户一眼看得出，
**被裁掉的选项用户根本不知道它存在**（他会以为这个模型就没有那一档）。

改法：把上限**算出来**而不是写死 —— 可用高度 =（上方/下方更宽裕的那侧
− 贴边 6px − 视口留白 12px），换算成浮层自己的单位后挂内联 `max-height`。
两种形态就都成立了：

- **装得下** → `scrollHeight === clientHeight`（完整显示，没有裁切）；
- **装不下** → 在边框内滚（滚动容器是浮层本身，配 `overscroll-behavior: contain`）。

**通则**：CSS 里凡是写死的 `max-height` / `max-width` 都要问一句
「超出之后用户看到的是什么」—— 是滚动条，还是**被无声裁掉的内容**。
后者要按剩余空间算，且必须同时给出「装不下」那一支的行为。

### ★★ `overflow-y: auto` 会把另一轴也算成 `auto`（2026-10-03）

用户接着报：「面板还是有左右的滚轮」（上一轮刚说「不要内容超出边界」）。

CSS 规范里有一条容易忽略的联动：**`overflow-x` 与 `overflow-y` 里只要有一个不是
`visible`，另一个是 `visible` 时就会被算成 `auto`**。所以「只想让竖着滚」这件事
**做不到**—— 只写 `overflow-y: auto` 的话，横向也变成 `auto`，
内容比内容盒宽一点点（实测 `scrollWidth 312` vs `clientWidth 297`，多 15px）
就冒出一条横向滚动条。

修法是两头一起：

1. **内容侧别让子元素比父级的内容盒更宽**。当时子元素的 `max-width: 300px`
   是照着**父级的边框盒**定的，而父级有 12px 内距 + 描边 —— 子元素于是比内容盒宽。
   改成「每段都 `width: 100%`」就再也对不上差了。
2. **显式写 `overflow-x: hidden`**，把「左右不可滚」变成不随内容漂移的硬约束。

**通则**：给容器加 `overflow` 之前先问「另一轴会变成什么」；
子元素的 `max-width` 要对齐的是**父级的内容盒**，不是它的 `width`。

### ★★ 同一条规则接在「三个来源」里的一个上（2026-10-03）

用户报：「我生成节点无论有没有素材的时候，只有 mj 模型有这个跟随素材的功能在比例的参数」。

`跟随素材` 这一档的规则很简单（用户 2026-09-24 定稿）：**这次生成有参考图就给，

   「我在 A 处写了规则」不等于「规则生效了」。
2. **症状会指向错误的方向**：`只有 MJ 有` 看起来像「MJ 特殊处理」，
   实际是「**恰好只有 MJ 走的那条路写了规则**」。找根因时先问
   「这条规则挂在哪一层？还有哪些路径绕过了它？」。

### ★ 上下文相关的取值别跟着「配方记忆」跑（2026-10-03）

同一个 bug 还有第二只脚：`ratio` 在配方记忆的名单里，于是「跟随素材」会被带进
**没有任何参考图**的新节点 —— 那个值此时没有可跟随的对象。

处理方式是**显示侧收口**而不是改记忆：面板发现「值是跟随素材、但这次没有参考图」
就显示成未设置（**不写回节点**，接上参考图它就该重新生效）；
请求侧本来就不会硬发（`buildRunPlan` 找不到参考图时如实不指定比例）。

**通则**：「依赖上下文才有意义的值」在两个地方要各设一道：
① 存的时候允许带（用户偏好，接上素材就生效）；
② 用/显示的时候必须校验上下文 —— 缺了这道校验，用户看到的是一个做不到的承诺。

### ★★ 官网读不到时怎么交付（2026-10-03）

用户说「去官网看一下」，而 **Midjourney 的三个域名全部回 403（Cloudflare 安全验证）**：

```
docs.midjourney.com / help.midjourney.com / www.midjourney.com
  → Node 直连 403；无痕系统 Chrome 打开是「正在进行安全验证」挑战页
  → 本机的浏览器控制通道也不可用（unsupported Codex auth method）
```

这种时候**不要假装查过了，也不要因此停掉整件事**。做法：

1. **如实写出处**：代码注释与文档里写明「值域取自**公开的官方参数表**，不是这一次从官网页面上读的」，
   并给出被挡住的证据（哪几个域名、什么状态码）；
2. 把「**待复核**」记进对账清单，而不是记成「已核实」；
3. 交付里**能确定的那部分照做**（面板形状、参数名、默认值这些用户已经给了参考图），
   把**不能确定的那部分明确留白**（例如 MJ 在中转站的端点与真跑验证、需要图床的引用类参数）。

**通则**：文档里的每一句「官方说的」都要能回答「你从哪儿读到的、什么时候读的」。
读不到就写「读不到」，那比一条编出来的出处安全得多。

### ★★ 猜出来的键名一旦被单测钉住，就再也没人怀疑它（2026-10-03）

用户报「Agnes Video 2.0 生视频不是按照我的全能参考来的」（插画风格的素材，出片写实风）。

真因是**参考图的键名**：`image`（单数）是**首尾帧 `keyframes`** 实测出来的
（错误原文 `mode=keyframes requires image as a list of at least 2 items`），
当初把它**顺手套用**到 `multi_reference` 上，而官方文档给 reference 模式写的是
**`images`（复数）** + `audios` / `videos`。上游只认复数 ⇒ 单数被**静默忽略** ⇒
参考模式退化成文生视频。

**为什么能藏这么久**：`openaiVideo.test.ts` 里那条用例断言的就是「发了 `image`」——
**被验证的是「我们发了什么」，不是「上游认不认」**。首尾帧那条标着「真令牌实测」，
参考那条**没有**，但两条用例的断言长得几乎一样，后来者扫一眼只会觉得「都验过了」。

三条教训：

1. **一次实测只能为它测过的那个东西背书**：同一个接口里 `keyframes` 收 `image`、
   `reference` 收 `images` 这种事，光凭「都是 Agnes 视频」是推不出来的。
2. **用例标题/注释里把「实测过」与「照文档写的」分开**：两种强度混在同一条用例里
   最容易骗人 —— 要么拆成两条，要么逐字段标明哪几个字是实测来的。
3. **键名不确定时两个都发**：这条链路的服务端对多余字段是宽容的
   （`size` / `aspect_ratio` 发过去不报错、只是不生效），同值发两个键只多一次命中机会，
   不换来 400；真被拒还有既有的 400 回落兜着。这比「赌一个」强，
   但**仍是兼容写法而不是结论** —— 必须写清「待真令牌复核」。

**顺带**：同一件事的另一半是**用法**。官方文档说 reference 模式要用
`<Picture N>` 指代输入素材 —— 提示词里不点名第几张图，模型没有理由照搬它的风格。
这类「文档写了、但用户在界面上看不到」的约定，值得直接写进面板（一行副标题就够）。

### ★★ 零成本「判别式探针」：塞非法类型，看错误指名到哪一层（2026-10-03）

上面的键名假设被真令牌推翻了，靠的是一个小手法：

**给字段塞一个类型非法的值**（`images: [123]` / `image: [123]`），让服务端的表单校验
**指名报错**。这样既不会真的排队生成（零成本），又能从错误里读出「它认不认这个键、期望什么类型」：

```
POST /v1/videos  { model, prompt, mode:'multi_reference', … , <待测字段> }

images: [123]  →  网关层   400 {"code":"invalid_json","message":"Failed to read request body"}
image:  [123]  →  转发到后端 400 … "Input should be a valid string"  param: "image.constrained-str"
不存在键 foo    →  （措辞落在上面两者之间，用来对照）
```

**关键认识：网关与后端是两层，错误措辞完全不同** ——
网关不认的键会说「读不出请求体」，后端不认的键会说「Input should be …」并指名到参数。
判定「键名对不对」这类问题时，先看错误来自哪一层，比读文档可靠得多。

顺带查明：这台中转站像是**多上游负载均衡** —— 同一条令牌会交替回
`200` / `401 Invalid token` / `429 rate limit for free users`。所以探针要**留间隔、允许重试**，
单次 401 不等于「令牌坏了」。

### ★★ 一次只改一条假设（2026-10-03，这条是给自己的）

上面那次修复我把**两个假设**打包上去了：① 复数键也许才是对的；② 不确定就两个都发。
结果是：把「两个键都发」这种**会让请求在网关挂掉**的形态推给了用户 —— 用户回「还是没有」，
而我当时没有证据说它比原来更糟。

**规矩**：一个改动只带一条可证伪的假设；「兼容性兜底」本身也是一条假设
（它假定服务端对多余字段宽容），要**单独验证**过再上。
发现方向错了就**明确回退**，并在对账里把「哪条推理被推翻」写清楚 ——
留着一条错的分析比没有分析更危险。

### ★ ParamPicker 的两张新面孔：滑杆与输入框（2026-10-03）

Midjourney 的高级设置需要「一根滑杆」和「一个文本框」，而 `ParamPicker` 原先只有
三种**选项**形态（list / pill / ratioGrid）。做法不是另写一个浮层，而是给它加两个
`variant`：`slider` 与 `text` —— 值仍沿 `value` + `onSelect(新值)` 走同一条路。

这么做的收益很直接：**定位、上下翻转、点外关闭、「同一时刻只开一个」、滚轮归属**
这些行为一个字都不用重写（另写一个浮层就要把这些再实现一遍，并且迟早分叉）。
两处小坑：

1. **「这一段有没有内容」不能只数 `options.length`** —— 滑杆/输入框没有选项，
   按选项数算会得 0，浮层直接显示成「没有可选项」。它们要各算一项。
2. **浮层宽度是 `max-content` 撑出来的**：比例网格（4×73+3×8）正好 316，
   而滑杆的固有宽度只有 120 出头 ⇒ 高级设置缩成一根 **167px 的窄条**。
   给滑杆行与输入框兜一个 `min-width: var(--picker-inner)`（316）才对齐。
