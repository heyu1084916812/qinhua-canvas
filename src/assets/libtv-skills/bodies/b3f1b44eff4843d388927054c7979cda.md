# 乙女互动影游创作

把用户的脑洞、小说、剧本或世界观转化为可制作、可扩展、可验证的乙女互动影游。默认玩家扮演女主或“你”，核心体验围绕主动选择、关系推进、主线危机和多结局回报展开。

## 工作原则

- 先建剧情地图，再写节点正文；不要一次性扩写全部路线和结局。
- 保留用户明确的题材、世界观、人物关系、时代、基调、平台、时长和结局要求。
- 女主必须拥有自己的目标、能力、秘密、资源和关键选择，不能只是被男主拯救。
- 每个关键选择必须改变至少一项后续内容：信息、关系、状态、资源、风险、路线、节点可达性或结局条件。
- 变量只服务剧情、信息、关系和分支解锁；不要擅自加入 RPG 等级、战斗公式或复杂数值成长。
- 采用“发散—回流/锁定—再发散”的可控结构，限制分支爆炸和制作成本。
- 任何分支都必须有可观察后果；禁止烟雾弹式选择。
- 每条可达路径最终必须抵达结局；节点、变量、目标ID和结局条件必须可验证。
- 失败、死亡和坏结局也是叙事结果，必须有完整情绪收尾。

## 工作流决策

根据用户任务选择阶段：

1. 只有脑洞或想法：读取 `references/workflow.md` 的阶段1，生成脑洞池或项目定位。
2. 要完整影游方案：执行阶段2—4，输出世界锚点、角色、剧情树、变量、分支和结局。
3. 要写某个节点：读取 `references/prompt-templates.md` 的节点模板，只扩写1个节点或连续2—3个节点。
4. 要写某条攻略线：使用路线模板，读取已确认的剧情树和变量字典，不改动主线结构。
5. 要写结局：使用结局模板，核对前置节点、条件、变量和路线锁定状态。
6. 要做选择后果审计：读取 `references/schemas.md` 的审计字段，逐项检查每个关键选择。
7. 要做路径测试：遍历剧情树，检查孤立节点、死循环、不可满足条件和无法收束的路径。
8. 要做程序化处理：先锁定剧情树和变量字典，再输出 JSON；如用户指定引擎，再映射为 CSV、Adventure Creator 或其他格式。
9. 要做分镜/资产：读取节点正文和资产字段，输出镜头、视频、音频、CG、道具和独立 `Prompt:` 行。

## 标准生产顺序

脑洞池 → 项目定位 → 总方案 → 剧情树 → 变量字典 → 节点细化 → 攻略路线 → 结局包 → 分镜/资产清单 → JSON/CSV/引擎配置 → 叙事与程序校验。

## 总方案最低交付字段

- 项目定位：玩家身份、核心体验、题材、基调、时长、平台、路线数、结局数。
- 世界锚点：时代、地点、规则、不可违背事实、视觉和内容边界。
- 角色关系：身份、目标、秘密、弱点、与女主关系、可改变状态、人物弧光。
- 变量字典：名称、类型、默认值、范围、改变来源、影响节点、是否可逆、影响结局。
- 剧情树：唯一节点ID、节点类型、前置条件、事件、选择、后续节点、回流/锁定/不可逆关系。
- 结局路径：结局ID、类型、触发条件、必经选择、变量要求、差异、情绪反馈。
- 互动节点：场景、人物、动作、对白、选择、即时反馈、变量变化、后果和后续节点。
- 资产信息：镜头、视频、音频、CG、道具、UI、文件命名和独立图像提示词。

## 默认变量类型

优先使用：`relationship`、`trust`、`counter`、`flag`、`item`、`evidence`、`identity`、`faction`、`risk`、`routeLock`、`state`。每个变量必须有实际剧情用途。

## 节点与程序化规则

- 节点ID全局唯一，推荐 `N00`、`N01A`、`N01B`、`E01`、`D01` 格式。
- 恰好1个 `start` 节点；普通小规模原型至少2个 `branch` 节点和2个实质不同的结局。
- 每个 `targetNodeId` 必须指向已定义节点。
- 每个条件引用的变量必须已经定义，且至少一条路径可以满足结局条件。
- 每个选择记录即时后果、延迟后果和路线关系；不能只记录好感度加减。
- JSON是程序化单一真相源；Markdown剧本和CSV/引擎配置均从它派生或与它逐项对照。

## 输出纪律

- 用户要方案时输出完整 Markdown，不输出思考过程。
- 用户要 JSON 时严格只输出合法 JSON。
- 用户要单节点时不要擅自扩写整条路线。
- 用户要资产时不要把资产提示词混入剧情正文。
- 不新增没有依据的核心设定；需要补全时标明为方案补全并服务主线。
